# 首页重设计

日期：2026-10-19
状态：设计稿，待批准后实施

## 1. 为什么要改

现状（线上实测的结构）：

```
nav    bindeep library  |  首页(自指) / 链接
h1     bindeep library          ← 与 nav 重复
p      bindeep 实验室 · …
img    微信二维码
p      微信公众号
nav    English | 中文           ← 夹在二维码后面
section  文章  → 1 条
```

问题不在配色或圆角，在**信息本身**：

1. **没有身份** —— 页面不说 bindeep 实验室是做什么的
2. **没有作品** —— bindec 藏在文章正文里，标题是《为什么 IDA 和 Ghidra 的都编不过》，扫过去只像个写反编译评论的博客
3. **没有联系方式** —— 潜在合作方看完不知道下一步
4. **导航有个「首页」自指链接** —— 点了就是当前页，不传达任何信息
5. **视觉重心错位** —— 90% 屏幕在讲一件可有可无的事

## 2. 目标读者

**潜在合作方**（主）。落��后应能在 30 秒内拿到：你是谁 / 你做过什么 / 怎么联系。

次要读者（仍要照顾，不能为了合作方牺牲）：搜索引擎、你自己回头查文章、微信分享进来的朋友。

## 3. 已定的决策

| 项 | 决定 | 来源 |
|---|---|---|
| 布局 | **A · 名片优先**（单栏纵向） | 讨论选定 |
| 配色 | **ink**（纸感米白 + 赭红 + 衬线） | 讨论选定 |
| 定位表述 | **目标式**：「正努力让……一致」，**不写「保证」** | 讨论选定 |
| 主要作品 | bindec（唯一一个） | 讨论确认 |
| 实验室方向 | 二进制程序分析和漏洞挖掘 | 用户提供 |
| 联系方式 | 微信二维码 + `bindeep.cn`，**不放邮箱** | 讨论选定 |
| 二维码位置 | 不再夹在副标题下，改为正式联系方式区块 | 讨论选定 |
| 语言 | 中英双份（`index.zh.md` / `index.en.md`） | 沿用既有双语结构 |

### 为什么不用「保证行为一致」

用户文章 §7 的实测：113/128（88.3%）编译通过，100/128（78.1%）重编译后退出码一致，
另有 13 个测试「编译通过但运行不一致」，其中 7 个在 C++ 类。首页若写「保证一致」，
读者点进文章看到 78.1% 与「已知未修完」，会认为首页在夸大。
故采用目标式表述，与文章数据不冲突。

## 6. 实现方式：raw HTML in Markdown

已实测（FSharp.Formatting 支持内嵌 HTML，探针 commit `88d835e`），
所以首页内容写在 `index.{lang}.md` 里，用少量 HTML + CSS 类实现作品卡与联系方式块，
**不需要改 F# 生成器的渲染逻辑**。

唯一必须动 F# 的是**语言切换器的位置**：现在它在 `<main>` 里（正文与文章列表之间），
而目标位置在 nav。要么改 F# 把它注入 header，要么用 CSS `order` 在 `main` 里上移。

- **推荐：改 F#**。让 `generateFinalHtml` 多接一个 nav 片段参数，
  `createIndexPage` 传「两个语言首页的链接」，`createPage` 传「本文各语言版本的链接」。
  语义清晰，CSS 不需要 hack。
- 备选：CSS `order`。改动更小但把结构问题藏进样式里，后续维护容易踩坑。

## 7. 需要你确认的点

**① 衬线字对长文的影响**

ink 主题设 `--font-family: Georgia, "Noto Serif", serif`，`styles.css:64` 的 `body` 会消费它，
`fonts/` 是空的。后果是**全站变衬线**，包括那篇 1171 行、含 24 个表格的文章。

- 中文长文用宋体是传统惯例（标题黑体、正文宋体），可读性未必下降
- 但**表格**用衬线通常更难读

三个选项：
- **a. 全站衬线**（直接换 tweaks.css，最简单）
- **b. 首页衬线、正文无衬线**（需要额外一条 CSS 规则，把 `--font-family` 限定在首页容器上）
- **c. 表格内强制无衬线**（只给 `table` 换字体，其余保持衬线）

我倾向 **c**：既保留 ink 的整体质感，又不牺牲表格可读性，改动也最小（一条 CSS）。

**② 作品卡要不要放硬指标**

你文章里有 113/128、0/128、22/128 这组实测数字，放在作品卡上说服力很强
（对手是 0% 和 17.2%）。但它们是**测试集内**的数字，放首页会被读成「普适水平」。

- 要放，就写清口径：「128 个测试程序上」
- 不放，就只有文字描述

我倾向**放，但标注口径**。

## 8. 验证方式

本项目无 dotnet、无测试工程，验证仍是「push → Actions → curl 线上产物」：

1. `scripts/verify.sh` 全绿（现有 12 个 URL 不变）
2. 中文首页与英文首页结构一致（区块顺序、CSS 类名）
3. 作品卡与联系方式在两版都可见
4. 二维码在 `/zh/` 与 `/en/` 下均 200（`<base>` 生效）
5. 文章页未被破坏（衬线字体下表格仍可读，需肉眼确认）
6. 无中文残留（英文版）、无模板作者残留

- 不改 `verify.sh` 的 URL 集合

## 10. 实施记录（commit `dcd335c`）

### 已确认的两项

① 表格强制无衬线、② 作品卡放指标并标注口径 —— 均按第 7 节的推荐执行。

### 实施中发现、已当场处理的三件事

**① `bindeep.cn` 不是这个博客，是产品站**

排查线上产物时才发现：`https://bindeep.cn/` 返回的是
**binforge · 智能反编译与漏洞分析平台**（`<title>` 与 meta description 确认），
与本博客（`https://bindeep-lib.github.io/`）是两个站点，且**产品站内没有任何链接指向博客**。

影响：原首页写「bindeep 实验室 · bindeep.cn 的实验性质博客」在事实上容易误读。
好在实验室方向「二进制分析和漏洞挖掘」与 binforge 的自我描述几乎逐字重合，
定位因此更自洽：实验室 → 工具 bindec → 产品 binforge（bindeep.cn）→ 博客记录过程。

**② 作品卡不能挂 bindec 的 GitHub 链接**

全站内容里唯一的 GitHub 地址是测试数据集 `bindeep-lib/DCB`，
**没有 bindec 仓库的地址**。编一个 URL 挂上去，若 404 反而伤可信度。
故作品卡链接改为已验证真实的 `bindeep.cn`，并把「测试数据集已开源」写进指标行
（对潜在合作方而言，benchmark 开源是比产品链接更强的可信度信号）。

> 若确实要把 bindec 仓库挂上去，需要仓库地址，补一行即可。

**③ 对比数字改用对手「修补后」的列**

初稿依据的是记忆中的「对手 0% / 17.2%」。核对文章后发现那只是
**原样编译**那一列；完整表格是：

| | ① 原样编译 | ② 修补后再编译 |
|---|---|---|
| IDA Pro 9.1 | 0 / 128 | **57 / 128** |
| Ghidra 12.1.4 | 22 / 128 | **44 / 128** |
| **bindec** | **113 / 128** | 不需要修补 |

首页引用**修补后**的 57 与 44 —— 那是对手的上限，也是唯一站得住的对比。
（引用 0 和 22 会显得我们在挑软柿子，而这篇文章的立场恰恰是不这么做。）

### 计划外新增：blockquote 取消斜体

ink 主题给 `blockquote` 加了 `font-style: italic`。文章里有 **69 处 blockquote**，
逐条看过，全部是**加粗的重点句**（「这不是能力高低，是产品定位不同」这类）。
浏览器对中文斜体是合成倾斜，既更难读，又恰好落在最该被记住的句子上。

因此在 ink 之上追加 `blockquote, blockquote p { font-style: normal; }`。
**这是第 7 节没有的一项**，属实施中新增，需用户确认是否保留。

### 探针：取消

原计划做一次独立的 `<div>` 探针页。实际未做 —— 改用**线上 `<img>` 的既有输出**作为证据：
线上 `/zh/` 里 `<img src="images/wechat-qr.jpg" alt="微信" width="180">` 连 `width` 属性
都被原样保留，说明 FSharp.Formatting 对 raw HTML 是逐字透传；`<div>` 属同一类 HTML block。
验证改为部署后直接 curl 首页，检查 `class="work-card"` 等标记是否原样出现。
探针页 `markdown-blog/probe.zh.md` 已删除，未进入任何一次提交。
