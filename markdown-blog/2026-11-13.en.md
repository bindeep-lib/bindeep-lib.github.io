# How compiler versions affect decompilation: 10 real-world cases

The same C source compiled once with gcc 9.4.0 (the one Ubuntu 20.04 ships) and once with gcc 15.2.0 (the one Ubuntu 26.04 ships) yields two binaries that behave identically at runtime. Feed both to a decompiler and the trouble begins: among the three decompilers, some outputs pass compilation straight away while others never make it past that first gate; and the fact that "the compiler version changed" leaves barely a trace in some outputs while showing up all over the place in others.

This article splits "how the compiler version affects decompilation" into 10 real cases, then settles the total with a three-way side-by-side run over 128 test cells (32 programs × 4 variants), answering three questions: which differences truly come from the compiler version and which are only the decompiler's own resource problem; which differences get written into the output text and which affect only semantics, invisible in the text; and how much these differences matter for "can the output be recompiled and run correctly".

Why we care about "recompiling": decompiled output is not the endpoint. Pipelines such as vulnerability analysis and patch verification have to compile the output back and run it; if it doesn't compile, there is no next step. So this is an engineering question.

The protagonists are three decompilers: IDA Pro 9.1 and Ghidra 12.1.4, the two mainstream tools, and bindec 1.0.2.

bindec 1.0.2 is the binary-decompilation module of the binforge platform (https://bindeep.cn/). binforge serves security researchers, reverse engineers and protocol analysts, with two main lines: precise decompilation and vulnerability mining; bindec belongs to the former — it recasts a binary into type-complete, symbol-complete C source that can be recompiled, and emits LLVM IR alongside. It has no interactive UI; it is built to be called in batch from pipelines, so its output is positioned as "a compilation unit for the compiler": it goes straight into gcc, and after relinking the program behaves like the original binary.

The criterion of this article (decompile → recompile → link → run → compare exit codes) was set to match that positioning. The three tools' outputs have different shapes, and one ruler applied to all three favors whom more: §1 covers output shape, §3 settles the ledger.

## 📌 The one-sentence answer: 5 of the 10 cases show up

Moving the compiler from gcc 9.4.0 to gcc 15.2.0 (language standard from C17 to C23) changes the instruction sequence of 189 of 354 user functions (53.4%). Most of those 189 changes are absorbed by pseudocode output "for humans to read" (the IDA / Ghidra style); what is truly version-related and leaves a trace in the output text comes down to 5 of the 10 cases. Switch the criterion (recompile the output and compare at run time) and the gap opens immediately: across 128 test cells measured three ways side by side, the double-pass rate is bindec 100% (128 / 128), IDA 40.6% (52 / 128), Ghidra 34.4% (44 / 128); recompiling the outputs with gcc 15.2.0 instead, the 64-bit end-to-end score leaves bindec at 64 / 64 and drops IDA and Ghidra by 6 cells each.

The 10 cases at a glance:

| # | Case | What gcc 15.2 changed relative to 9.4 | Visible in pseudocode? | How the three tools fare |
|---|---|---|---|---|
| 1 | Stack-protection canary | xor replaced by sub | Conditionally shows up | IDA absorbs it; Ghidra shows it conditionally; bindec shows it (^ becomes -) |
| 2 | One extra hop at call sites | One extra hop loading arguments, order reversed | Absorbed | bindec must recover it at register level, or the output won't compile |
| 3 | Sign extension | cltd/cdq replaces the sar idiom | Invisible in text, may be semantically wrong | Only a run-and-compare finds it |
| 4 | Function epilogue and frame layout | rbx moved from push to a stack slot | Indirectly visible (offset carrier) | All three outputs carry offset traces |
| 5 | Jump tables | Off by default at -O0 | Conditionally shows up | No instance in this corpus; no extrapolation |
| 6 | DWARF 4→5 | Library type graph disappears, destructor description changes | Shows up | Only IDA / Ghidra affected; bindec does not depend on DWARF |
| 7 | vtable and EH | New C++ exception cleanup branches | Shows up | All three outputs grow branch traces |
| 8 | Library function identification | No difference between the two gcc versions | Cross-tool difference | IDA has built-in intrinsics; Ghidra is fully blind offline |
| 9 | __gmon_start__ | No difference on the input side | Does not show up | Weak symbols don't enter pseudocode |
| 10 | Language standard C17→C23 | Missing declarations turn from warning to hard error | Shows up | IDA / Ghidra lose 6 cells each |

## 🔬 First, the test corpus, the two gcc versions, and the criterion

The corpus: the public test set DCB (github.com/bindeep-lib/DCB), 32 source files × 4 variants (x64 / x86 × dynamic / static linking), 128 test cells in total, called cells throughout. 32-bit takes half on purpose, and everything is compiled at -O0.

The compiler has two axes: gcc 9.4.0 (Ubuntu 20.04 default, C17) and gcc 15.2.0 (Ubuntu 26.04 default, C23, with -fzero-init-padding-bits=all added explicitly).

There is exactly one criterion, unchanged throughout: decompile → recompile → link → run → compare the exit code with the original binary. "Compiles" counts only compilation; "double-pass" requires both compile and run to pass.

Three things we set ourselves, stated up front because they shape how to read the numbers below:

| Self-set item | Who set it | What it decides | What's left without it |
|---|---|---|---|
| The criterion (compile + run + exit-code compare) | Us | Replaces "does the output look like C" with "does it pass a compiler and run correctly" | Only text comparison remains; semantic differences like Case 3 become completely invisible |
| bindec's own regression test set (135 cases, only 6 of them 32-bit; 540 / 540 green on 64-bit) | The project team | It is a "known-issues list": 32-bit coverage is too thin, and many 32-bit defects were previously out of view | The 32-bit findings in this article still stand, minus the explanation of "why nobody saw them earlier" |
| Relaxed post-processing for the rivals' output (IDA: 27 regex rules + C++ class stubs; Ghidra: 18; bindec: 0) | Us | Lets IDA / Ghidra output get through compilation as much as possible | The numbers are conservative in bindec's favor (see §3) |

## 1. Pseudocode vs compilation unit: output shape decides sensitivity

First a piece of real IDA output (variadic-function scenario):

```c
int main(int argc, char *argv[], char *envp[])   // three parameters were guessed
{
  __readfsqword(0x28u);                          // no declaration
  ...
  // va_list is only a stack-slot comment, with no type source
```

Hand this output to gcc as-is and it reports 9 hard errors: my_printf, va_start, va_arg, __readfsqword and _stack_chk_fail are all implicit declarations; va_arg(args, uint64_t) doesn't even expand, because stdarg.h is missing and the macro never opens up — it lands as a plain syntax error. Pseudocode's stance is "the reader will fill in": types, declarations, macros are left to the person looking at the code.

bindec's stance is different: it emits a compilation unit that compiles on its own. Under C23 a missing declaration is a hard error; a missing macro is a hard error under any language standard; mixing pointers with integers is a hard error; a declared type that doesn't match actual usage is also a hard error. The compiler spares nobody, so declarations, macros and types must all be recovered one by one.

The stance difference sets up the two main lines every later case hangs on:

1. **Output shape decides sensitivity.** Pseudocode's observable surface is "does this look like a piece of C": as long as semantics are equivalent, most instruction-level shape differences are absorbed and the output text barely moves. A compilation unit's observable surface is "what the machine code looks like": every operator and every intermediate register has to be turned back into legal C, so shape differences land straight in the text.
2. **The "visibility" of version differences is therefore layered.** The same input-side difference may be fully invisible in pseudocode, while a compilation unit must handle it explicitly or its output won't compile.

Both shapes in one table:

| | Pseudocode (IDA / Ghidra) | Compilation unit (bindec) |
|---|---|---|
| Written for | Humans | The compiler |
| Missing declaration / macro | Assumes the reader will fill it in | Hard error, output won't compile |
| Instruction-shape differences (an extra hop, xor becoming sub) | Mostly absorbed, text barely moves | Must be recovered explicitly, lands in the text |
| Sensitivity to version differences | Low; the price is that compilation was never going to pass anyway | High; the payoff is output that recompiles and runs |

## 2. The 10 real cases

Each case first checks the input side (do the two gcc builds actually differ, and where), then looks at the three decompilers' outputs. "Visibility" has three levels: shows up (the difference lands directly in the output text), conditionally shows up (lands in the text only under specific conditions), absorbed (invisible in the text).

### Case 1 · Stack protection (canary): xor becomes sub

Input side: for the stack-guard check, gcc 9.4.0 emits `mov -0x8(%rbp),%rcx; xor %fs:0x28,%rcx; je`, gcc 15.2.0 emits `mov -0x8(%rbp),%rdx; sub %fs:0x28,%rdx; je`. union_basic, multi_dim_array and class_basic share the same shape.

- IDA: folds the whole thing away. union_basic's output is left with `return 10;` plus a thunk; the check logic is completely invisible. Absorbed in the classic sense.
- Ghidra: for union_basic it renders a self-inequality that is always false, `if (*(long *)(in_FS_OFFSET + 0x28) != *(long *)(in_FS_OFFSET + 0x28))`. Going back to the input side, the root cause is not xor / sub: upstream there were already the two instructions `mov %fs:0x28,%rax; mov %rax,-0x8(%rbp)`, and the two versions' Ghidra output is byte-for-byte identical (down to `PTR___stack_chk_fail_00404000`). But in virtual_func Ghidra can tell the stack slot from the TLS value, and the comparison operator flips between versions: the 9.4 output is `!=` with fail-then-return, the 15.2 output is `==` with return-then-fail — semantically equivalent. Conditionally shows up.
- bindec: the canary is visible across the whole chain. The TLS read becomes the placeholder `__thread long long __bindec_tls_64_p40`; the failure branch is recovered as `#define function_401040() __stack_chk_fail()`; main gets `__attribute__((optimize("no-stack-protector"))) int main_inner` so stack protection isn't re-injected on recompilation; the two TLS reads become two variables v2 / v10; xor is recovered as C's `^` (the 15.2 build's counterpart is `v10 = v2 - v8`, matching the input-side sub); `if (!v12)` is not folded away, and prototypes and calls are all present. The whole stack-protection mechanism survives.

This case also separates two meanings of "can't see it": for IDA it is absorption (the difference went into its abstraction layer); Case 9 will show the other kind, a decompiler that has no such nerve at all.

### Case 2 · One extra hop at call sites: pseudocode flattens it, a compilation unit must recover it explicitly

Input side: variadic_printf's main goes from 14 instructions to 15. gcc 15.2.0 moves `lea …,%rdx` earlier and adds the hop `lea …,%rcx; mov %rcx,%rdi`, reversing the argument-loading order overall. This "one extra mov copy after a lea" shape accounts for 16.9% of the 189 differing functions (39.2% under a looser count).

- IDA / Ghidra: absorbed into `my_printf("x=%d, y=%s\n", 42, "hello")` (42 versus 0x2a is only spelling), the extra hop disappears.
- bindec: must recover the correspondence between formal parameters and actual arguments at register level. If it fails, the output won't compile — a hard requirement.

### Case 3 · Sign extension: invisible in the text, possibly wrong in value

Input side: gcc 15.2.0 does sign extension with the cltd / cdq instructions; gcc 9.4.0 uses the `sar $0x1f,%eax` idiom — 1.6% of the 189 differing functions.

Searching all 128 variants' three-way outputs for cdq, cltd, idiv and sar hits nothing: this difference never appears as text, only as a semantic result, e.g. `v29 = &v44[v28 / 2];` (func_ptr_dispatch's IDA output). It is the only case among the 10 that is "invisible in the text, possibly wrong in value semantics": if cltd is modeled as zero extension, a negative dividend computes wrongly while the output text still reads `/ 2`. Pseudocode flattens the text but not the semantics, which is why the "run and compare" step cannot be skipped.

### Case 4 · Function epilogue: the indirect carrier of frame-layout change

Input side: class_basic's main goes from 38 instructions to 37. gcc 9.4.0 ends the function with `add $0x18,%rsp; pop %rbx; pop %rbp`, gcc 15.2.0 with `mov -0x8(%rbp),%rbx; leave`: rbx moves from push / pop to a stack slot, and the frame layout changes with it.

- IDA: `int arr[2][3][4]; // [rsp+10h] [rbp-70h] BYREF` — the change lands in the comment's offsets.
- Ghidra: `uint8_t local_b8 [8]; uint64_t local_b0; local_a8; …` — locals named by offset.
- bindec: frame layout is the base input for recovering locals and arguments. The implementation's discriminating factor is "is this slot a stack slot or a register", independent of which basic block the write happens in, so this kind of frame change leaves it untouched.

The difference itself isn't directly readable, but it is the carrier of stack-slot offsets — indirectly visible.

### Case 5 · Jump tables: conditionally visible, no instance in this corpus

Input side: gcc 15.2.0 disables jump tables at -O0 by default (`-fjump-tables [disabled]`), so a dense switch degrades into a decision tree. But the only switch_case in DCB uses sparse cases (values 1..5), for which gcc 9.4.0 already generated a decision tree; on the input side the two versions are identical for this program.

- IDA: `return 15;`.
- Ghidra: `return 0xf;`, plus 4 `WARNING: Removing unreachable block (ram,0x00401142)` lines.
- bindec: has two jump-table recovery abilities: jump-table inference, and .rodata byte-array dispatch-table recognition.

This corpus contains no instance that triggers the jump-table difference, so this entry only registers the phenomenon; no extrapolation.

### Case 6 · DWARF 4→5: the library type graph disappears, destructor descriptions change

Input side: gcc 9.4.0 writes DWARF4, gcc 15.2.0 writes DWARF5 (DW_UT_compile). The business types are present in both: Point with 1 struct / 3 members, 1 enum, 1 union with 2 members, Counter gaining 1 member; types.c's home-made types Own / UsedHdr / used_hdr_t totaling 2 structs / 1 typedef / 4 members. What changes is the library type graph: in the source file that only uses printf, gcc 9.4.0's DWARF carries FILE / _IO_FILE / _IO_marker / _IO_codecvt / _IO_wide_data plus 32 members, and in gcc 15.2.0 all of it disappears (struct, typedef and member counts all drop to 0). The mechanism sits in the external-variable DIEs: gcc 9.4.0 writes DW_TAG_variable for stdin / stdout / stderr, dragging the FILE type graph in; gcc 15.2.0 no longer does. DW_AT_frame_base is DW_OP_call_frame_cfa in both versions — version-independent.

- Ghidra: keeps DWARF original-prototype comments, 54 occurrences over 20 files, e.g. `/* DWARF original prototype: void Counter(Counter * this, int v) */`, with `Point p;` / `Color c;` / `U u;` / `Counter c;` in the output. Once the library type graph is gone, the "get types from DWARF" road carries its risk on Ghidra's side.
- IDA: 0 prototype comments. struct_basic folds straight to constants as `return 60;`; the C++ cases keep `Counter c; // [rsp+4h] [rbp-1Ch] BYREF` plus `Counter::Counter(&c, 10);`.
- bindec: has a fallback of "skip DWARF parsing when it crashes, fall back to the symbol table", with a narrow trigger surface (variable-length arrays plus a few DWARF5 encodings); when it triggers, stderr carries the warning `Warning: DWARF loading crashed ..., skipping DWARF info.` — nothing is swallowed silently. In practice gcc 15.2.0's struct_basic produces no warning, and its output is line-for-line identical to the 9.4 build (`uint32_t p = 10;`, the variable name p comes from DWARF, the struct is flattened into scalars). Library types don't depend on DWARF: for the `FILE *f = stdin;` case, bindec automatically emits `#include <stdio.h>`, `uint64_t f = stdin;`, `fputc(120, (FILE *)f);`, the type coming from its bundled headers.

An incidental find: for the destructor ~Counter (linkage name `_ZN7CounterD4Ev`), the DW_TAG_formal_parameter entries — gcc 9.4.0 writes two (this and int, both with DW_AT_artificial), gcc 15.2.0 writes only one (this; the second entry is Abbrev Number: 0). Ghidra's destructor signature therefore differs across versions: `Counter::~Counter(&c,__in_chrg);` plus `void __thiscall Counter::~Counter(Counter *this,int __in_chrg)`, versus the single-parameter version `Counter::~Counter(&c);`. All 5 differing lines in Ghidra for this case come from this; IDA's two versions are byte-for-byte identical. We only claim "the DWARF description differs" here; the ABI itself was not verified (objdump did not locate the symbol — no direct evidence).

### Case 7 · vtable and EH: cleanup branches are the bulk of semantic visibility

Input side: virtual_func's main goes from 49 instructions to 62. After the operator new call site, gcc 15.2.0 inserts `mov $0x0,%eax; test %al,%al; je` plus an operator delete cleanup branch — this is a C++ exception landing pad: it disappears under -fno-exceptions and survives -fno-check-new, ruling out the "allocation-failure check" explanation. The temporary-register chain for taking the vtable address switches from 9.4's %rdx chain to 15.2's %rax chain. The 53.4% (189 / 354 user functions) instruction-sequence change between the two versions surfaces in pseudocode mainly as these added branches.

- IDA: `LODWORD(v4) = (*((int64_t ( **)(Circle *))shapes->_vptr_Shape + 2))(shapes);`; plus `int64_t operator new(uint64_t a1)` and `void operator delete(void *a1, uint64_t a2) { _ZdlPvm(a1, a2); }`.
- Ghidra: `iVar2 = (*(this->super_Shape)._vptr_Shape[2])(this);`; the vtable assignment `(_func_int_varargs **)&PTR__Square_00403d68`; operator new goes through the GOT (`PTR_operator_new_00404018`); operator_delete appears, plus 2 `unreachable` WARNINGs (ram,0x004011b9).

Two easily misread points:

1. Address-bearing symbol names are diff noise. Going from gcc 9.4.0.2 to 9.4.0.3, a point-version bump alone moves `PTR__Square` from 00403d68 to 00403d50; while between the two major versions 9.4 and 15.2 it happens not to move (both are 00403d50). Whether an address moves depends on layout, not on the version axis.
2. Slot numbers (`+ 2` / `[2]`) are decided by class layout (DWARF) and don't change between versions: `[2]` appears twice per version in Ghidra's output.

### Case 8 · Library function identification: a cross-tool difference, none between the two gcc versions

Input side: between the two binaries, the library functions themselves have no version difference. The difference visible to the eye is on the decompiler's resource side:

- IDA: the signature library sig/pc/ holds 137 .sig files in total, with no gcc-version-specific x64 set; the only file with gcc in its name, gcc32rtf.sig, has nothing to do with gcc-on-linux. For the same canary bytes, IDA emits `v7 = __readfsqword(0x28u);`, coming from the Hex-Rays x86 processor module's built-in intrinsics — gcc-version-independent, 188 occurrences over 42 files across the corpus. PLT stubs are self-referential recursive thunks: `int vprintf(...) { return vprintf(format, arg); }`.
- Ghidra: the installation carries 0 .fidb FID libraries (FID requires going online and downloading per processor + compiler + version; offline, there is effectively no library-function identification). The same bytes render as `lVar1 = *(long *)(in_FS_OFFSET + 0x28);` — 373 occurrences over 26 files; plus 8 C++ cases hitting __readfsqword, 64 occurrences over 32 files in total. PLT stubs go through GOT indirection: `PTR_vprintf_00404020`.
- bindec: takes the "broad coverage, accept slower" road; compiler-specific patterns recognize only a single version, backed by generic signatures; scanning is on the slow side, in exchange for offline availability — a hard requirement for automated pipelines.

Conclusion: the difference visible to the eye here (IDA and Ghidra giving different names to the same bytes) belongs to "resource availability" and is easily misread as "compiler version"; nothing changed between the two gcc versions.

### Case 9 · __gmon_start__: a pseudo-difference with no input-side difference at all

Input side: both versions have __gmon_start__, with the same WEAK UND attributes (130 / 130 and 133 / 133 of the outputs carry it); this is a crt / glibc property, unrelated to the compiler version. Across the three-way outputs of the 32 × 4 variants it appears 0 times: weak symbols don't enter pseudocode.

One bindec-side note: in the ELF it is a function, but crt's _init reads the corresponding GOT entry as data — both a function and used as data, with nowhere to put a prototype, so the output is left with the bare name, which C reports as undeclared at compile time. The criterion must rest on "what it is used as"; what the symbol table calls it is secondary. On the bindec side this dangling reference fails at link time, identically in both versions.

The lesson of this case: version differences must be verified independently on the input side first (objdump / readelf); never work backward from tool output. Case 7's address noise and Case 8's resource difference both easily go wrong at exactly this step.

### Case 10 · Language standard C17→C23: missing declarations go from warning to hard error

Input side: DW_AT_producer changes from `GNU C17 9.4.0` to `GNU C23 15.2.0 … -fzero-init-padding-bits=all`. Compiling the 32 x64 dynamic variants' outputs with each gcc in turn:

| Output from | Compiles under gcc 9.4.0 | Compiles under gcc 15.2.0 | Fail both | Fail only under C23 |
|---|---|---|---|---|
| IDA | 16 / 32 | 10 / 32 | 16 | 6 |
| Ghidra | 11 / 32 | 8 / 32 | 21 | 3 |
| bindec | 32 / 32 | 32 / 32 | 0 | 0 |

The failure nature differs: all of IDA / Ghidra's new failures are missing declarations (implicit declaration of process / compute / classify) — under C17 that is only a warning, under C23 it becomes a hard error, so IDA drops from 16 / 32 to 10 / 32 and Ghidra from 11 / 32 to 8 / 32. bindec is 32 / 32 under both versions: it never takes the implicit-declaration road — in the previous round, bindec's failures in this column were illegal types (`initialization of 'uint64_t' from 'char *'`, `passing argument 1 of 'longjmp' from incompatible pointer type`), not missing declarations; once that batch of type problems was fixed, both versions pass clean, not one dropped.

The 64-bit end-to-end scoreboard is in §3: bindec 64 / 64 unmoved, IDA and Ghidra each lose 6; not repeated here.

### Summary: 5 of the cases are version-related and leave a trace in pseudocode

| Case | How it shows up |
|---|---|
| 1 canary | Conditionally shows up (bindec, conversely, shows it: ^ becomes -) |
| 5 jump tables | Conditionally shows up (no instance in this corpus) |
| 6 DWARF | Shows up (holds only for IDA / Ghidra; not triggered for bindec in practice) |
| 7 vtable / EH | Shows up (in shape) |
| 10 C23 | Shows up |

The other 5: Case 8 is visible to the eye but is a cross-tool difference; Case 2 is absorbed by pseudocode (bindec must handle it explicitly); Case 3 is invisible in the text and may be semantically wrong; Case 4 is indirectly visible; Case 9 has no input-side difference at all.

## 3. Three-way side-by-side run: the ledger over 128 cells

**First, the numbers least favorable to us:** this section has two timelines. In the previous round, bindec had 21 failures on these 128 cells, all of them on 32-bit, 8 of them the decompiler itself crashing (no output could be produced at all); bindec then fixed that batch of 32-bit shape defects and re-ran on the same inputs with the same criterion: 128 / 128 all pass. The table below is the post-retest result — the failure rate is a function of the version, not of the corpus.

| Caliber | bindec | IDA | Ghidra |
|---|---|---|---|
| Compiles | 128 / 128 (100%) | 57 / 128 (44.5%) | 44 / 128 (34.4%) |
| Compile + run double-pass | 128 / 128 (100%) | 52 / 128 (40.6%) | 44 / 128 (34.4%) |
| x64 double-pass | 64 / 64 | 26 / 64 | 22 / 64 |
| x86 double-pass | 64 / 64 | 26 / 64 | 22 / 64 |
| C++ subset double-pass | 32 / 32 | 0 / 32 | 0 / 32 |
| Total failures | 0 | 76 | 84 |
| Of which won't compile | 0 | 71 | 84 |
| Of which compiles but runs differently | 0 | 5 | 0 |

The C++ subset on its own: bindec compiles 32 / 32, double-passes 32 / 32; IDA and Ghidra are all 0 / 32 — not one compiles. bindec has zero failures on both 64-bit and 32-bit.

Three structural conclusions:

1. On the 44 common cells all three tools can handle, the run-match rate is 100% (44 / 44). Compilation ability and semantic recovery are two orthogonal things.
2. Reading it the harder way: of the 76 cells IDA fails and the 84 cells Ghidra fails, bindec passes every one. There is not a single cell where "the rival passed and bindec failed" — not one in this round.
3. The price: for static binaries, bindec's output is about 3× its rivals' in size (it lays out glibc / libstdc++ stub functions).

Fairness caliber: IDA's output got 27 post-processing regexes plus C++ class stubs and compiles with -fpermissive; Ghidra got 18; bindec got none. The numbers above are conservative in bindec's favor.

As-is direct compilation caliber (no patching of any kind, no -w / -fpermissive): bindec goes from 117 / 128 (91.4%) to 117 / 128 (91.4%) — not one cell different across the two versions; IDA drops from 56 / 128 (43.8%) to 41 / 128 (32.0%); Ghidra from 44 / 128 (34.4%) to 32 / 128 (25.0%). The cause is still missing declarations (implicit declaration of apply, double_it undeclared): under C23 warning becomes error, costing IDA and Ghidra 15 and 12 cells respectively. bindec's own 11 as-is failures are all strict C++ type conversions (`narrowing conversion of '252'`, `invalid conversion from 'uint64_t' …`); the 24 C cases pass 96 / 96 — whether output passes the compiler in strict mode has nothing to do with the compiler version; it depends on whether the decompiler wrote the types correctly.

(In this round, both gcc versions' 32-bit C++ standard headers were complete; the "missing bits/c++config.h makes all three fail, cell excluded" situation never occurred, so this column has no excluded cells.)

Linking caliber: the harness's recompile always links dynamically (`g++ -w -no-pie … -lc -lm -lpthread -lstdc++`). The static inputs' original binaries are statically linked, and bindec's output references internal symbols shared libc doesn't export (__wcsmbs_gconv_fcts_c), so under the dynamic caliber linking fails; relinking statically in the original mode (-static) makes it pass. So the comparison numbers are slightly worse than the project's own regression caliber, stated here as-is. gcc 15.2.0's static axis: 0 / 32 under the dynamic caliber, 31 / 32 relinked statically in the original mode — the entire difference is the link mode.

End-to-end scores for recompiling the outputs with a different gcc version (64-bit cells):

| Output from | Recompiled with gcc 9.4.0 | Recompiled with gcc 15.2.0 | Change |
|---|---|---|---|
| bindec | 64 / 64 (100%) | 64 / 64 (100%) | unmoved |
| IDA | 26 / 64 (40.6%) | 20 / 64 (31.2%) | loses 6 |
| Ghidra | 22 / 64 (34.4%) | 16 / 64 (25.0%) | loses 6 |

All the new failures are missing declarations (implicit declaration of compute / process / classify). bindec is full in both directions: its code compiles under both gcc versions and produces the same exit codes.

### The previous round's 21 failures: shapes, details, and two independent corroborations

This subsection is kept for comparison. In the previous round, bindec really did have 21 failures on these 128 cells, all on 32-bit: 8 decompiler crashes of its own (the C++ try_catch / inherit_single / virtual_dtor / virtual_func — no output could be produced); 10 SIGSEGVs (func_ptr_callback, struct_return_large / small, class_basic, template_class); 2 wrong results (variadic_sum sums wrongly); 1 environment anomaly (variadic_printf's 32-bit static variant, fine after a manual relink — an execution-environment issue). They fall into four shapes: cdecl struct-by-value return (sret), variadic va_list, function pointers taking structs, and C++ destructors and vtables.

Corroboration 1: comments on same-named programs in bindec's own regression corpus had long recorded these shapes ("on 32-bit, struct returns are forced through a stack copy", "variadic stack-argument passing translates wrongly", "call-convention translation is wrong when a function pointer is an argument", "dispatch tables are not recognized"), but the corresponding cases only ever compiled the 64-bit builds in the regression set. All green did not mean problem-free — the cases just never got hit.

Corroboration 2: retesting in a clean 32-bit environment with recompiled inputs. That earlier batch of inputs had faulty 32-bit link parameters, so we built a clean environment, recompiled the 21 failing cases' source files, and reran the same pipeline: 19 / 21 failure shapes matched field-for-field (including the 8 crashes); both variadic_sum runs "computed wrongly" but with different wrong values (stack-layout misalignment); the new inputs compiled 21 / 21 (gcc 9.4.0.2 to 9.4.0.3). Conclusion: that was not measurement error, nor an input anomaly — it was that bindec version's real 32-bit defects.

This round's retest: same inputs, same criterion, all 21 failures gone, 128 / 128, with the fixes for the four shapes all landing on the 32-bit path. This subsection is kept not to showcase fix speed, but to make a different point — a "mostly green, a few red" distribution is the easiest to be fooled by: an all-green regression set may simply never have hit those 21 cases.

### Output byte-diff: the 32 x64 dynamic variants compared byte by byte

(Static variants don't count: the libc content itself differs.) Byte-for-byte identical: IDA 29 / 32 (90.6%), Ghidra 27 / 32 (84.4%), bindec 0 / 32. After normalizing the version comments inside the outputs: IDA 29 / 32, Ghidra 27 / 32, bindec 16 / 32 (50.0%). This round was re-measured with each gcc version's own outputs; bindec is still 0 / 32 and still 16 / 32 after normalization — byte-for-byte the same as the previous round.

IDA / Ghidra's differing 3–5 are all C++ cases (inherit_single / virtual_dtor / virtual_func / class_basic / try_catch), caused by Case 7's EH cleanup branches. bindec changes in all 32 / 32: some differ only in the comment gcc (9.4.0) becoming gcc (15.2.0); 16 differ in the code itself (^ becoming -, explicit casts, EH cleanup paths).

To close the mechanism: pseudocode's output follows the semantics; change the compiler version and it barely moves — the price is that differences are all absorbed and compilation was never going to pass anyway. A compilation unit's output follows the machine code; it is inherently sensitive to version differences, in exchange for output that recompiles, runs, and exposes semantic differences like Case 3's.

## 4. How to reproduce: from the DCB corpus to three-way recompilation

### 4.1 The two gcc axes

Prepare two toolchains, gcc 9.4.0 and gcc 15.2.0, each installed under its own prefix; at test time, put the corresponding version's bin directory at the front of PATH and leave the other at /usr/bin/gcc as a control.

### 4.2 The test set

```bash
git clone https://github.com/bindeep-lib/DCB
cd DCB && bash build.sh
```

The four variants' build parameters: dynamic `gcc -O0 -no-pie -g`; static `gcc -O0 -no-pie -g -static -D_GNU_SOURCE=1`; 32-bit adds -m32 (.cpp goes through g++). Note that -m32 needs gcc-multilib — without it, all 128 variants quietly become 64-bit.

### 4.3 The three decompilers

```bash
# bindec
bindec-decompiler bin/enum_basic_x64_dyn -o out/enum_basic_x64_dyn.c
```

Ghidra runs through PyGhidra (pip install pyghidra, using DecompInterface to emit pseudocode). IDA runs through idalib (pip install ., then run py-activate-idalib.py, then `import idapro, ida_auto, ida_hexrays`). Two notes: idalib binds CPython 3.11, and idapro must be imported first; the three tools must run serially (IDA's backend temp script writes to a fixed path — running in parallel, they stomp on each other).

### 4.4 Recompiling and the criterion

```bash
gcc -c -w -O0 -no-pie out/foo.c -o foo.o
gcc foo.o -o foo -lc -lm -lpthread
./foo; echo $?
```

Compare the exit code with the original binary. C++ output uniformly uses `g++ -c -w -O0 -no-pie -fpermissive -std=gnu++11` plus -lstdc++, and a helper header declaring only __stack_chk_fail and __readfsqword, injected with -include — identical treatment for all three. Static inputs are relinked statically in the original mode (hidden symbols like __wcsmbs_gconv_fcts_c are not exported by dynamic libc). The fairness caliber once more: IDA / Ghidra's outputs received relaxed patching (the official __fastcall macro, source-level patching with C++ class stubs); bindec did not get a single line of patching.

### 4.5 Input-side verification

objdump -d for instruction sequences; readelf -p .comment for the compiler version; readelf --debug-dump=info for DWARF. Ghidra 12 needs JDK 21 (JDK 17 reports unsupported); offline, the FID libraries are 0 .fidb files, which matches the in_FS_OFFSET-style output rendering.

Endnote: bindec is at version 1.0.2; every number in this article comes from one fixed environment and one fixed round on the same test machine, reproducible per section 4; bindec is the binary-decompilation module of the binforge platform (https://bindeep.cn/ ).

## Last

Scope first: the conclusions cover only the measured combinations — DCB's 32 programs, the two gcc versions 9.4.0 and 15.2.0, -O0, x64 and x86, dynamic and static linking. Other compilers, other optimization levels, other corpora: no extrapolation.

A two-step standard for readers, taken in order: step one, verify independently on the input side (objdump / readelf against the two versions' binaries) that the difference truly comes from the compiler version; step two, pick the caliber. To know "did the difference leave a trace in the output", read the text diff; to know "is the output still usable", accept only compile-plus-run double-pass. The two calibers give opposite impressions (in the byte-diff section bindec changed in 0 / 32 — that is, all of them — yet holds the highest double-pass rate of the three); that is not a contradiction, just a different observable surface.

Next steps: on the bindec side, the four 32-bit shapes are fixed and retested clean; the remaining visible shortcoming is the 11 strict C++ type conversions under the as-is compilation caliber. For IDA / Ghidra users to clear the C23 gate, adding declarations to the output is the most direct step. Which decompiler to choose depends on what the output is for: for humans to read, IDA / Ghidra's pseudocode is friendlier; to feed a compiler, the output must first clear the compilation gate.

Want to try it yourself: the binforge platform is at https://bindeep.cn/ — upload a binary and get back recompilable C source with LLVM IR emitted alongside.
