# Decompiled output: why won't IDA's or Ghidra's code compile?

> 128 test programs, measured three ways side by side
> **bindec 1.0.2** / IDA Pro 9.1 / Ghidra 12.1.4 · same test set, same compile commands, same criterion
> bindec is our own decompiler: it turns a compiled binary straight back into C code **a compiler can consume**. "Decompilation" refers exactly to that recovery process.
> IDA is a commercial reverse-engineering tool from Hex-Rays; Ghidra is a reverse-engineering suite open-sourced and donated to the community by the U.S. National Security Agency (NSA) — what they produce is pseudocode **for humans to read**.
> Caliber: the IDA / Ghidra numbers were measured in 2026-10; the bindec numbers were measured on 2026-11-12 (current 1.0.2 build). Test set, compile commands and criterion are identical.

**Every number that is unflattering to us is written next to IDA's and Ghidra's failures: never set apart, never buried in an appendix.**

---

## 📌 The one-sentence answer

**Because the three tools were being asked to do two different things in the first place.**

IDA and Ghidra produce **pseudocode for humans to read** — the implicit contract is "the person reading the code will fill in what is missing".
bindec produces **compilation units for the compiler** — the implicit contract is "the compiler will guess nothing for you".

**The test has only two steps, and the final score counts only after both are run:**

**① Throw the decompiled output at gcc as-is** — compile, link, run.
Not one of IDA's 128 outputs compiles; Ghidra gets 22 through.

**② For everything that fails to compile, patch the source and run again** — we wrote 23 regex rules for IDA and 18 for Ghidra, and generated C++ class shells for both.

| | ① Compiles as-is | ② Compiles after patching | Compiles **and** runs correctly |
|---|---|---|---|
| IDA Pro 9.1 | **0 / 128** | **57 / 128** | 52 / 128 |
| Ghidra 12.1.4 | **22 / 128** | **44 / 128** | 44 / 128 |
| **bindec 1.0.2** | **128 / 128** | **no patching needed** | **128 / 128** |

bindec's 128 / 128 is not the finish line — it is bought at a price: performance and scale, output size, laid out as they are in chapters 7 and 8.

## 🔬 First, how the experiment was run

Every "test binary × tool" pair goes through these four stages, and **every number in this article comes from one of them**:

| Stage | What it does | What it measures |
|---|---|---|
| **Stage 1** | Decompile | Produces the **raw output** (the C the decompiler emitted directly) |
| **Stage 2** | `gcc -c` the raw output | Measures **raw output quality** |
| **Stage 3** | Patch the source of the raw output | Add declarations, rewrite syntax, inject C++ class shells; **bindec skips this stage** |
| **Stage 4** | `gcc -c` → `ld` → execute | Measures whether it is actually usable |

> Here, **"source patching"** means rewriting pseudocode-style constructs into standard C so it will compile, plus adding the missing declarations and injecting C++ class shells.

**bindec goes 1 → 4; IDA / Ghidra go the full 1 → 2 → 3 → 4.**

| Number | Comes from |
|---|---|
| The headline table: 100% / 44.5% / 34.4% | Stage 4 |
| Raw output: 0% / 17.2% | Stage 2 |
| Syntax problems vs semantic problems, broken down | Stage 2 |
| Distribution of failure causes; share of missing declarations/types | Stage 4 |

> ⚠️ **The headline table comes from stage 4, not from "tossing the raw output at gcc".**
> We applied 23 / 18 regex rules for IDA / Ghidra and generated C++ class shells —
> **only bindec's output goes straight into gcc.** Chapter 4 quantifies that contribution separately.

**On where the data comes from:**

- Versions under test: **bindec 1.0.2 (2026-11-12 build)** / IDA Pro 9.1 / Ghidra 12.1.4.
  The IDA / Ghidra columns carry over from the 2026-10 three-way run and were not re-measured; bindec was fully re-run on 2026-11-12 with the current build (128 cells, one run, not stitched together).
  **Changing versions can change the conclusions** — every percentage here answers for these specific versions.
- The "runs correctly" criterion is exit-code comparison, one case at a time: the 32 test programs' original exit codes are all non-zero with 24 distinct values, and the exit code of the recompiled decompiled output must match. They were designed non-zero and spread apart on purpose, because **"compiles but runs wrong" is the most dangerous failure mode** — neither "does it crash" nor "is the exit code 0" catches it (full commands in the reproduction chapter).
- 128 test programs × 3 tools = 384 decompilations, **from a single run**, not stitched together across time.
- The compile command is identical across all three: `gcc/g++ -c -w -O0 -no-pie [-m32]`, with C++ additionally getting `-fpermissive -std=gnu++11`.
- The test dataset is open source: https://github.com/bindeep-lib/DCB

## 1. Answer one question first: who actually needs it to compile?

Before any numbers, there is a question that cannot be skipped:

> **Isn't decompiled code just meant for people to read? Why does it have to compile?**

Without answering it, everything after this hangs in the air.

---

### 1.1 "Readable" and "compilable" are two different things

**"Readable" is for humans.** You see a comment saying "unknown calling convention, but parameter storage is locked", you realise the author wasn't sure either, you mentally fill in the rest and move on. Nobody minds.

**"Compilable" is for machines.** A compiler does not fill in gaps. It sees a variable named `Color`, so it must find a definition of `Color`; it sees a call to `operator_new(...)`, so it must find that function. **If it cannot, it errors out and gives you nothing extra.**

An analogy:

| | Pseudocode (for people) | Compilation unit (for machines) |
|---|---|---|
| Implicit contract | The reader is a person, **who knows how to fill in the gaps** | The reader is a compiler, **it guesses nothing for you** |
| Analogy | A recipe written for an experienced cook | A blueprint handed to a machine |
| Writing "a pinch of salt" | The reader judges | **straight to compile failure** |
| Writing "3 g salt, cast iron pan, 180 °C" | Also readable | ✓ anyone following it gets it right |

In one line:

> **IDA and Ghidra give you the former, bindec gives you the latter. That is a difference in product positioning, not in capability.**

---

### 1.2 So who actually needs it to compile?

Decompiled code gets used for roughly three kinds of work. **Their requirements for "compilable" differ enormously.**

#### ❌ Not needed: single-point analysis

**Malware sample analysis.** You just want to know what this suspicious program does. Look at its behaviour, run it in a sandbox, read a few key functions. That's enough.

In that scenario IDA's and Ghidra's on-demand decompilation is **markedly faster** — they decompile only the function you ask about, and do nothing until you ask. This is also how most people use a decompiler day to day.

#### ⚠️ Partly needed: targeted auditing

**Commercial software audits.** You only audit the few modules you care about, say payments or authentication. You don't need complete source for the whole binary.

The part being audited does compile under IDA. Using IDA there is perfectly fine.

#### ✅ Must compile: exhaustive and automated

In the scenarios below, **"doesn't compile" is not a blemish — it breaks the entire pipeline outright.**

**① Automated vulnerability scanning**

This is the most typical example, because behind it sits a **capability asymmetry** across the whole industry:

- **Source-level** scanners are far more mature than **binary-level** ones — Clang Static Analyzer, CodeQL, Semgrep, cppcheck, with ever finer checkers
- **Large models** read source far better than they read binaries directly

Stack the two and the conclusion follows: **you cannot scan anything until you have turned the binary back into source.**

```text
binary
  |
  ↓  decompile — if it doesn't compile, everything breaks right here
  |
source  →  SAST engines + LLMs  →  vulnerability report
```

> SAST: Static Application Security Testing — scanners that find vulnerabilities by reading source without running the program.

And all of those tools **consume source only, never pseudocode**. A function that doesn't compile is simply beyond them.

Worse is **completeness of the decompilation**.

If 20 of 100 functions don't compile, the vulnerabilities inside those 20 never appear in the report — and the scanner will not warn you "I could not see 20 functions".

> **A function that does not compile does not exist as far as the scanner is concerned — even if the most severe vulnerability is sitting inside it.**

**② Legacy migration / maintaining old systems**

The manufacturer is gone, the compiler is too old, the hardware is out of production. You want to rebuild an old program on a new system.

The bar here is higher than in ①: ① only needs it to compile, ② needs the result to **link and run**.

And "migration" means producing a new binary — if it cannot be compiled, the remaining work is not maintenance, it is **rewriting from scratch**.

**③ AI training data**

The question most deserving an answer, and most easily glossed over: **"why not just train on source?"**

**Because in a great many cases, source is not among the options.**

Closed-source software and industrial firmware ship as binaries only; games and commercial libraries distribute binaries only; some projects once had public source, but the repository is now deleted and only the binary remains.

The bottleneck for training data has never been "the highest-quality code" — that is available on GitHub at any time — it is **the code you can obtain stably, legally, and at scale**.

And when the model itself has to read binaries (vulnerability hunting, reverse engineering, binary repair, closed-source Q&A), training on source means
**the training distribution and the inference distribution don't match**. Train a model that only ever saw `.c`, hand it a `.so`, and it knows nothing.

> `.c` is a C source file, `.so` is a compiled shared library. Having only seen one during training and being handed the other at inference
> is asking the model to reason from the wrong experience.

More decisively, the ground truth for these tasks lives on the binary side — source says what the author **meant** to do, the binary says what **actually runs**.

**④ Binary rewriting / binary repair**

First, one distinction: **patching** and **rewriting / repairing** are not the same thing.

Patching — changing bytes directly in the binary — needs **no** source. A hex editor can turn `74` (`je`) into `75` (`jne`). So "binary patching" is precisely the case that does **not** need compilable source, and this section's argument does not apply to it.

The real need is **rewriting / repairing**: the vendor no longer maintains the software and the source is unobtainable, but you must change the program's behaviour —
add a bounds check around an out-of-bounds access, replace a hard-coded key with an externally injected one, or instrument an old function to find out when it is actually called.

All of these changes are **semantic**. You are not flipping a flag bit; you are changing program logic.

There is exactly one reliable path: **decompile → modify source → recompile → replace the binary**.

> Here, "recompiling" is not an option — it is **the only option**.
> If the source doesn't compile, the path is broken: either fall back to byte patching (which only supports very local changes), or give up on the repair.

---

### 1.3 So the difference is not capability, it is the goal

> **IDA / Ghidra want to "understand the few functions you care about".**
> **bindec wants to "hand you a codebase you can compile yourself".**

The former is **on demand**. The analyst clicks a function and only that function is decompiled; missing things the analyst adds themselves in the type manager, then asks for the next one.

The latter is **in bulk**. Nobody sits in front of bindec clicking a mouse; it has to emit **every** libc function prototype, **every** struct definition,
and **every** PLT thunk (under static linking, each libc function leaves a stand-in in the output) all by itself.

**The cost of that path is very visible; chapter 7 accounts for it in full.**

## 2. A counter-intuitive number

We compiled 128 small programs into binaries, handed them to three decompilers to turn back into C, then handed **the C the decompilers emitted**
to gcc (`gcc -c` → link → execute → compare exit codes).

| | Compiling the output **directly** | Compiling after source patching | Exit code correct after link+run |
|---|---|---|---|
| **bindec 1.0.2 (2026-11-12)** | **128 / 128 = 100%** | **no patching needed** | **128 / 128 = 100%** |
| IDA Pro 9.1 (2026-10) | **0 / 128 = 0.0%** | 57 / 128 = 44.5% | 52 / 128 = 40.6% |
| Ghidra 12.1.4 (2026-10) | **22 / 128 = 17.2%** | 44 / 128 = 34.4% | 44 / 128 = 34.4% |

> **bindec's second column is "no patching needed"** — its output enters gcc with no processing at all, so the first and third columns are already the final result.
>
> **The first column for the other two is the real score for "raw output"**: not one of IDA's 128 outputs compiles, and Ghidra gets only 22 through.
> The extra numbers in the second column are what our processing bought them.
>
> The third column is measured on whichever output each tool *could* compile — bindec on its direct output, the other two on their patched output.
>
Ghidra has 106 tests that **do not even compile as raw output**, and 84 of them still fail after source patching. What does failing to compile mean?
It means you never even get the chance to find out "whether this program computes the right thing or the wrong thing" — the compiler stops you at the first gate.

Before explaining that number, one sentence that may be unwelcome: **this is not a story about "bindec being smarter than IDA".** IDA and Ghidra are the best tools in this field; they have simply been asked to do something entirely different.

## 3. Two wildly different kinds of output

There are two kinds of decompiler output, and the difference is much larger than most people assume.

---

### The first kind: pseudocode — what IDA / Ghidra produce

Its implicit contract is: **"the reader is a person, and that person knows how to fill in what's missing."**

An analogy: it is like **a recipe written for an expert cook**:

> "a pinch of salt" "simmer gently for 20 minutes"

You understand perfectly well what it means, but you cannot follow it — how many grams? How high the heat? What pan?

Ghidra will even leave you a comment in the output:

```c
/* WARNING: Unknown calling convention -- yet parameter storage is locked */
```

Translated, that means: **"I don't know how this function passes its parameters, but I've written down the way I guessed."**

---

### The second kind: compilation unit — what bindec produces

The requirement is: **"the reader is a compiler and it guesses nothing for you."**

The same recipe, but every step is spelled out: 3 g of salt, cast iron pan, 180 °C, 20 minutes. Leave out one item and it fails — but as long as it is complete, anyone can follow it.

That is why an IDA user never worries about "what is this struct called": the analyst opens the type manager and fills it in. bindec has no interactive UI, so it has to emit every libc prototype, every struct definition and every PLT thunk by itself.

> **Where bindec's 100% (128 / 128) and IDA's patched 44.5% (57 / 128) mostly come from is not better decompilation accuracy — it is a different positioning of the output.**
>
> But positioning is not everything: the price bindec pays for it — performance and scale, output size — is laid out with numbers in chapters 7 and 8. We do not intend to sum this product up with 128 small programs all passing.

## 4. ⭐ We patched the source — why does it still not compile?

Those "missing declarations" and "missing types" above read like "the other two are just bad". But a fairness question has to be put on the table first:

> **What patching did we do to make IDA's and Ghidra's output compile?**

The answer is blunt: **a fair amount.** The comparison framework applies the following processing to IDA's and Ghidra's output:

| | IDA path | Ghidra path | bindec |
|---|---|---|---|
| Number of source-patching regex rules | **23** | **18** | **0** |
| Generate C++ class stubs | yes (injected into 32 test combinations) | yes (injected into 32 test combinations) | no (outputs its own) |
| Add `-fpermissive` at compile time | yes | yes | yes |

None of those 41 rules is "fixing code" — every one is a **textual substitution over the output**, replacing words the decompiler invented with ones gcc recognises. Grouped by purpose:

**① Strip MSVC calling conventions (5 rules for IDA)**

```python
re.sub(r'\b__fastcall\b',    '', content)
re.sub(r'\b__cdecl\b',       '', content)
re.sub(r'\b__stdcall\b',     '', content)
re.sub(r'\b__thiscall\b',    '', content)
re.sub(r'\b__vectorcall\b',  '', content)
```

These five words are MSVC keywords that gcc has never heard of. IDA prints them in front of every function, so **every single** output dies at the compiler's first gate.
> That is basically where "IDA 0.0% (0 / 128)" comes from: **117 files fail to parse outright, and the remaining 11 die on other words.**

**② Swap private type names for standard types (16 for IDA + 14 for Ghidra)**

| Tool | Before | After | Count |
|---|---|---|---|
| IDA | `_QWORD` / `_DWORD` / `_WORD` / `_BYTE` / `BOOL` | `uint64_t` / `uint32_t` / `uint16_t` / `uint8_t` / `int` | 5 |
| IDA | `unsigned __int64` … `__int8` | `uint64_t` … `int8_t` | 8 |
| IDA | `__noreturn` | deleted | 1 |
| IDA | `_UNKNOWN` | `void` / `void *` | 2 |
| Ghidra | `undefined1/2/4/8/16`, `undefined` | `uint8_t` / `uint16_t` / `uint32_t` / `uint64_t` / `__uint128_t` / `void` | 6 |
| Ghidra | `sbyte` / `byte` / `word` / `dword` / `qword` | `int8_t` / `uint8_t` / `uint16_t` / `uint32_t` / `uint64_t` | 5 |
| Ghidra | `processEntry` / `__noreturn` | `__attribute__((noreturn))` | 2 |
| Ghidra | `(code *)` | `(void (*)(void))` | 1 |

In this category, **the type information is actually all there** — `_QWORD` is 8 bytes, `undefined8` is also 8 bytes. What is missing is only a standard C name, and supplying it is enough.

**③ Whitespace and pointer-star normalisation (2 for IDA + 2 for Ghidra)**

```python
re.sub(r'  +', ' ', content)        # collapse runs of spaces into one
re.sub(r' +\*', ' *', content)      # "int  * x" → "int * x"
```

Purely cosmetic. **gcc only warns about these, and `-w` silences them** — but they make the output look broken.

**④ Two things unique to Ghidra**

| Rule | Handling |
|---|---|
| `ram:ff001000` | replaced with `0` — Ghidra's pseudo-addresses are not real addresses and gcc cannot use them |
| `FUN_00104080` | **looked up in the symbol table and replaced with the real function name** — kept as `FUN_*` only if `nm` has nothing |

**⑤ Four extra rules IDA needs on the C++ tests** (outside the 23 above; C++ only)

These four are not counted in the 23 — they run only when `LANG == "cpp"`:

| Rule | Handling | Why it is needed |
|---|---|---|
| `RETURN_TYPE Class::method(Type *this) { ... }` | **deleted entirely** | IDA emits the full member-function definition too, and keeping only the calls inside `main` is enough |
| `Counter::~Counter(&c)` | rewritten as `c.~Counter()` | gcc does not accept IDA's destructor-call form |
| `void __stack_chk_fail() { ... }` | **deleted entirely** | it conflicts with the C++ shell we inject |
| standalone `{ ; }` empty body | deleted | the leftover shell after the previous rule is removed |

> Of the 41 rules, only one uses any information from the binary itself; the rest are all word substitutions. And by the measure of the headline table, Ghidra still has 84 outputs that will not compile even after patching —
> **this class of failure, a missing semantic, cannot be rescued by any number of rules.**

**And bindec does zero source patching — its output goes straight into gcc.**

---

### C++ class stubs: generated, but they only "keep it compiling"

Beyond word substitution, the framework also **generates C++ class shells**. The logic has three steps:

**① Scan the output for `ClassName::`**

```python
class_pattern = re.compile(r'\b([A-Z][A-Za-z0-9_]*)\s*::')
referenced_classes = set(class_pattern.findall(content))
```

**② Filter out standard-library noise** (`std`, `string`, `vector`, `map`, `cout`, …), then emit a block per remaining class:

```cpp
class Animal {
public:
    void *opaque_data;        // opaque data, stands in for the real members
    void *_vptr;              // vtable pointer
    void *_vptr_Dog;          // ← one vtable pointer per referenced class
    Animal(...) { }           // constructor: empty implementation
    static int speak(...) { return 0; }   // ← every non-destructor member is static and always returns 0
};
```

**③ Inject it right after `#include <stdint.h>`.**

But this shell has a hard flaw: **it can only guarantee "compiles", never "runs correctly".**

---

### The result of the two stages

That pipeline above was never a single pass; it was **designed to measure two passes**:

```text
                      ┌───────────── Pass 1: as-is ─────────────┐
  IDA/Ghidra: decompile ──▶  raw output ──▶ gcc ──▶ 0.0% / 17.2%
  bindec:      decompile ──▶  output     ──▶ gcc ──▶ 100%        (no patching needed)

                      └───────────── Pass 2: patched ─────────────┘
  IDA/Ghidra:          raw output ──▶ source patching ──▶ gcc ──▶ 44.5% / 34.4%
```

So the table below reads simply: **the left column is pass 1, the right column is pass 2, and the gap in between is what those 41 rules bought.**

Same set of binaries, same compile commands, same moment.

| | **Pass 1**: compiled as-is | **Pass 2**: compiled after patching | Contribution of those 41 rules |
|---|---|---|---|
| **IDA Pro 9.1** | **0 / 128 = 0.0%** | 57 / 128 = 44.5% | **+44.5 pp** |
| **Ghidra 12.1.4** | **22 / 128 = 17.2%** | 44 / 128 = 34.4% | **+17.2 pp** |
| **bindec 1.0.2** | **128 / 128 = 100%** | n/a (the output was compilable to begin with) | — |

> **bindec's row is not the same kind of thing as the other two rows.** Its output compiles on pass 1,
> so there is no "patching" stage — for it those 41 rules are **a built-in stage of the pipeline**, not an external remedy.

---

### Where do the failures of stage 2 actually sit?

We sorted the **first** gcc error of every failing cell into two layers:

- **Syntax problems**: the tool used its own vocabulary — `__fastcall`, `_QWORD`, `undefined8`, `@<n>`, stray spaces. A few regexes convert them to standard C, **without needing to understand what the program does**.
- **Semantic problems**: missing type definitions, missing function declarations, wrong C++ member-call syntax. **You first have to work out what this was supposed to be**, which means actually understanding the binary.

| | Syntax problems | Semantic problems |
|---|---|---|
| **IDA** (128 stage-2 failures) | **96.9%** (117 parse failures caused by `__fastcall` + 7 leftover `@<n>`) | **0%** |
| **Ghidra** (106 stage-2 failures) | 32.1% (Ghidra-specific type names `undefined1/2/4/8`) | **56.6%** (32 missing declarations + 24 missing types + 4 signature conflicts) |

---

### Decisive evidence: the generated C++ stubs rescued exactly 2

The "smartest" part of the framework is generating C++ class shells for the output:

```c
class Counter { public: void *opaque; void *_vptr;
                static int add(int) { return 0; }   // ← every member function returns 0
              };
```

We scanned the output directly to check its actual effect:

| | Compiles | Of which contain an injected stub | Fails to compile | Of those also contain a stub |
|---|---|---|---|---|
| **IDA** | 57 | **2** | 71 | 30 |
| **Ghidra** | 44 | **0** | 84 | 32 |

**Injected into 64 outputs (cpp-oop is 8 tests × 4 variants = 32 test combinations, × 2 tools), it rescued 2 for IDA and 0 for Ghidra.**

**Those 2 "rescues" count as compiles but are necessarily wrong at runtime** — every member function in the stub `return 0`, and the exit codes went from 13 / 60 to 0.

## 5. Broken apart: five real examples

Chapter 4 gave you the "two layers" conclusion, but readers will still have a plainer question: **what specifically fails to compile?**

The five examples below all come from real output measured in this run, reproduced verbatim (paths elided). Between them they cover the main shapes of failure.

> **Syntax problems** — defects at the level of C grammar, which a machine can recognise and replace in bulk.
> **Semantic problems** — involve "what this type, this function actually is"; the information is not in the output and has to be read back out of the binary.

---

---

### Example 1 · IDA: one word kills the whole file — `__fastcall`

This is the easiest to understand and the one that best shows what "syntax problem" means. Here is the original source:

```c
// enum_basic.c
enum Color { RED = 1, GREEN = 2, BLUE = 3 };

int main(void) {
    enum Color c = GREEN;
    int sum = 0;
    switch (c) {
        case RED:   sum = 10; break;
        case GREEN: sum = 20; break;
        case BLUE:  sum = 30; break;
    }
    return sum;  // expected exit code 20
}
```

**IDA's stage-1 output (no source patching at all) is 12 lines in full:**

```c
// Auto-generated by IDA Pro 9.1 idalib
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>

// Function: main
int __fastcall main(int argc, const char **argv, const char **envp)
{
  return 20;
}
```

gcc's reaction:

```text
enum_basic_x64_dyn_raw.c:8:16: error: expected '=', ',', ';', 'asm' or '__attribute__' before 'main'
    8 | int __fastcall main(int argc, const char **argv, const char **envp)
      |                ^~~~
```

Note how much rides on this: **`return 20` is completely correct** — the enum, the switch, all three branches were constant-folded by IDA into 20 without losing anything.
It "loses" purely because of the single word `__fastcall ` in front of the function name, and that word is **an MSVC calling-convention macro that exists only inside IDA's own type database**, which gcc has never heard of.

Compare the same file after one regex from our framework:

```c
// Function: main
int main(int argc, const char **argv, const char **envp)
{
 return 20;
}
```

**One word: from 0% (0 / 128) to compiling.** This is what IDA's 96.9% (124 / 128) "syntax problem" failures look like:
the decompilation is not wrong, **IDA generated a statement the compiler does not recognise.**

---

---

### Example 2 · Ghidra: uses the type name but does not give you the definition — `Color` / `Point`

Same `enum_basic.c` (source in example 1), Ghidra's output:

```c
/* === main */

/* WARNING: Unknown calling convention -- yet parameter storage is locked */

int main(void)

{
 int sum;
 Color c;

 return 0x14;      // 0x14 = 20, equally correct
}
```

```text
enum_basic_x64_dyn_ghidra.c:12:2: error: unknown type name 'Color'
   12 |  Color c;
      |  ^~~~~
```

This one is more interesting: **Ghidra recognised that `c` has a type called `Color`**, so it confidently wrote `Color c;`.
But it **used only the name and did not emit the `enum Color { ... }` definition** — because in Ghidra's world that does not matter,
the analyst can fill it in through the type manager.

The same shape recurs throughout the test set:

```text
error: unknown type name 'Point'; did you mean 'int'?     ← struct_basic.c: user struct not recovered
error: unknown type name 'U'                              ← union_basic.c: user union not recovered
error: unknown type name 'binop'                          ← function-pointer typedef not recovered
```

**Notice the `did you mean 'int'?` hint** — gcc had to treat `Point` as an undeclared identifier and guess.
Nobody, looking at that output, ever learns how many bytes `Point p;` occupies or how it is laid out.

**This category is fundamentally different from example 1**: regexes cannot touch it. Whether `Color` should be RED=1/GREEN=2 or something else
exists only in the original program's type information — **you cannot invent it without understanding the binary**.

### Example 3 · IDA + Ghidra: the symbols are right there in the binary, but no declarations were generated

`func_ptr_callback.c` calls three of its own functions:

```c
int double_it(int x) { return x * 2; }
int triple_it(int x) { return x * 3; }
int add_one(int x)   { return x + 1; }

int apply(int x, int (*op)(int)) { return op(x); }

int main(void) {
    int s = 0;
    s += apply(10, double_it);   // 20
    s += apply(10, triple_it);   // 30
    s += apply(20, add_one);     // 21
    return s;                    // 71
}
```

IDA's output:

```c
// Function: main
int main(int argc, const char **argv, const char **envp)
{
 int s; // [rsp+Ch] [rbp-4h]
 int sa; // [rsp+Ch] [rbp-4h]

 s = apply(10, (int (*)(int))double_it);
 sa = apply(10, (int (*)(int))triple_it) + s;
 return apply(20, (int (*)(int))add_one) + sa;
}

// Function: apply
int apply(int x, int (*op)(int))
{
 return op(x);
}
```

```text
error: 'double_it' undeclared (first use in this function); did you mean 'double'?
error: 'triple_it' undeclared
error: 'add_one' undeclared
```

**And the symbols for those three functions are sitting in the binary perfectly well:**

```console
$ nm func_ptr_callback_x64_dyn
000000000040112e T add_one
0000000000401141 T apply
0000000000401106 T double_it
0000000000401161 T main
0000000000401118 T triple_it
```

Names, addresses, symbol types — all present. **It is not that "the information was lost", it is that "it was not written out"** — IDA treated these three functions as data (function pointers)
rather than call targets, so it emitted bodies for `main` and `apply` and yet never emitted three declarations for them.

Compare bindec's output, which does two things:

```c
// ------------------- Function Prototypes --------------------

static inline __attribute__((always_inline)) uint32_t add_one(int32_t a1);
static inline __attribute__((always_inline)) int32_t apply(int32_t a1, char * a2);
static inline __attribute__((always_inline)) uint32_t double_it(int32_t a1);
static inline __attribute__((always_inline)) uint32_t triple_it(int32_t a1);

// ------------------------ Functions -------------------------

// Address range: 0x401106 - 0x401118
static inline __attribute__((always_inline)) uint32_t double_it(int32_t a1) {
    return 2 * (uint32_t)a1;
}
...
```

**Wherever a function pointer is referenced as data, a declaration must be supplied.** bindec additionally recognised the function-pointer dispatch inside `apply`
and recovered all three candidate targets (that part of the output is itself ugly, but it compiles, runs correctly, and exits with 71).

This example shows the difference in contract between the two kinds of output most clearly: IDA's assumption is "you can click into it inside IDA", so it writes no declarations;
bindec's assumption is "the compiler cannot see IDA", so it must write them.

### Example 4 · Ghidra: treats `this` as an ordinary variable — member functions written as static functions

`inherit_single.cpp` is the simplest possible single inheritance:

```cpp
class Animal {
public:
    virtual ~Animal() {}
    virtual int speak() { return 0; }   // 0 = generic
};

class Dog : public Animal {
public:
    int speak() override { return 1; }  // 1 = woof
};

int main() {
    Animal* a = new Dog();
    int result = a->speak();
    delete a;
    return result;
}
```

In Ghidra's output, `main` looks like this (excerpt):

```c
int main(void)

{
 int iVar1;
 Dog *this;                    // ← it declared a local variable called this
 int result;
 Animal *a;

 this = operator_new(8);
 (this->super_Animal)._vptr_Animal = (_func_int_varargs **)0x0;
 Dog::Dog(this);
 iVar1 = (*(this->super_Animal)._vptr_Animal[2])(this);
 if (this != (Dog *)0x0) {
 (*(this->super_Animal)._vptr_Animal[1])(this);
 }
 return iVar1;
}
```

gcc reports 4 errors in total, **every one of them different**:

```text
error: expected unqualified-id before 'this'                    ← this is a C++ keyword and cannot be a variable name
error: invalid use of 'this' in non-member function            ← main is an ordinary function; where would this come from
error: 'operator_new' was not declared in this scope           ← it wrote operator_new(...) itself just above
error: 'super_Animal'                                        ← that base-subobject member is absent from the generated stub
```

The last of these is worth singling out. To rescue Ghidra, our framework **generates C++ class shells**, roughly like this:

```cpp
class Animal { public: void *opaque_data; void *_vptr;
               void *_vptr_Animal;
               Animal(...) { }
};
class Dog { public: void *opaque_data; void *_vptr;
            void *_vptr_Animal;
            Dog(...) { }
};
```

You can see the problem at a glance: **the shell only knows the three patterns `opaque_data` / `_vptr` / `_vptr_<baseclass>`,
whereas what Ghidra actually emits is the "base subobject" spelling `super_Animal`. The shell and the output do not match.**

Worse, every member function body in the shell is an empty `{ }`, which means **it always returns an undefined value**.
That is where chapter 4's "64 injections rescued only 2" comes from — even when the shell does match, it can only guarantee "compiles", never "runs correctly".

The same root problem on `inherit_multi.cpp` looks like this:

```text
error: 'class C' has no member named 'super_A'    ← three-level inheritance; the member name in the shell no longer matches
```

> **This is the hardest of the five examples.** It is not "a missing declaration" — it is that **the entire C++ object model is wrong**:
> how the vtable is laid out, at which byte of the base the subobject sits, what the constructor does — that information *is* in the binary,
> but translating it back into something C can express requires a **real C++ decompiler**, which no number of regex rules can deliver.

### Example 5 · IDA: uses a macro that exists only inside IDA — `LODWORD`

`virtual_func.cpp` is virtual-function polymorphism. Here is IDA's `main`:

```c
{
 Circle *v3; // rbx
 Square *v4; // rbx
 Circle *shapes; // [rsp+10h] [rbp-30h]
 Square *shapes_8; // [rsp+18h] [rbp-28h]

 v3 = (Circle *)operator new(0x10u);
 Circle::Circle(v3, 4);
 shapes = v3;
 v4 = (Square *)operator new(0x10u);
 Square::Square(v4, 5);
 shapes_8 = v4;
 LODWORD(v4) = (*((int64_t ( **)(Circle *))shapes->_vptr_Shape + 2))(shapes);
 return (uint32_t)v4 + (*((int64_t ( **)(Square *))shapes_8->_vptr_Shape + 2))(shapes_8) + 2;
}
```

```text
error: 'LODWORD' was not declared in this scope
```

`LODWORD(x)` is **IDA's internal macro for "take the low 32 bits"**, a standard facility in IDA's type database.
It looks harmless, but it is in no standard header.

Interestingly, **the same file hides another problem**:

```c
// Function: .__stack_chk_fail
// attributes: thunk
void __stack_chk_fail()
{
 _stack_chk_fail();      // ← it invented a function it has no way to verify
}
```

IDA built a shell for the stack-protector mechanism, and the shell calls an **unexported** internal symbol from glibc — so
`virtual_func` **compiles but fails to link**:

```text
/usr/bin/ld: virtual_func_x64_dyn_ida.o: in function `__stack_chk_fail':
undefined reference to `_stack_chk_fail'
```

**This example is a textbook sample of "guessing"**: IDA does not know what the real stack-protector function looks like, so it invented a shell;
and it cannot even verify that shell itself — because the target it calls is not exported by glibc at all.

**The same defect shows up once more, on another test, `pointer_arith`:**

```text
/usr/bin/ld: pointer_arith_x64_dyn_ida.o: in function `__stack_chk_fail':
undefined reference to `_stack_chk_fail'
```

The reason is written in IDA's own output:

```c
// Function: .__stack_chk_fail
void __stack_chk_fail()
{
  _stack_chk_fail();      // ← it invented a function it has no way to verify
}
```

### The five examples summarised

| Example | Shape | Which layer | How hard to fix |
|---|---|---|---|
| 1. IDA `__fastcall` | decompilation is **correct**, the shell just doesn't recognise it | syntax problem | **one regex** |
| 2. Ghidra `Color` / `Point` | uses the type name without giving the definition | semantic problem | hard — you need to know the type layout |
| 3. IDA `double_it` | the symbol is in the binary, no declaration written | semantic problem | medium — just add the declaration |
| 4. Ghidra `this` / `super_Animal` | the C++ semantic model is wrong entirely | semantic problem | **hardest** — needs a real C++ decompiler |
| 5. IDA `LODWORD` / `__stack_chk_fail` | uses an internal macro; and guesses wrong | syntax problem + semantic problem | first half one regex, second half unfixable |

## 7. ⚠️ Cost one: slow — and where it is slow

All good news so far; this chapter is about the price — and the price is glaring.

We measured all three tools on the same batch of test binaries (every cell: same binary, same machine, CPU idle).
**The bindec column was measured on 2026-11-12 (current 1.0.2 build); the IDA / Ghidra columns were measured in 2026-10**;
the sample binaries are rebuilt by the test set's `build.sh` each time — same sources, sizes as actually built:

| Sample | Size | bindec 1.0.2 | IDA (2026-10) | Ghidra (2026-10) |
|---|---|---|---|---|
| `if_else_simple` dynamically linked x64 | 17 KB | **0.4 s** | 0.64 s | 1.69 s |
| `variadic_printf` dynamically linked x64 | 18 KB | **0.5 s** | 0.39 s | 2.00 s |
| `virtual_func` (C++) dynamically linked x64 | 21 KB | **0.6 s** | 0.68 s | 1.81 s |
| `if_else_simple` statically linked x64 | 799 KB | **2.8 s** | 6.16 s | 33.28 s |
| `variadic_printf` statically linked x64 | 800 KB | **3.1 s** | 7.29 s | 35.60 s |
| `setjmp_longjmp` statically linked x86 | 714 KB | **2.0 s** | 4.49 s | 35.75 s |
| `virtual_func` (C++) statically linked x64 | 895 KB | 10.2 s | 6.36 s | 38.09 s |

> Dynamically linked: the program loads libc at runtime; statically linked: libc is baked into the binary at compile time.
> That is why static samples are an order of magnitude bigger, and the time grows with them.

**At this scale bindec is not slower than IDA and Ghidra — on static binaries it is 3.7 to 17.8× faster than Ghidra and 2.2 to 2.4× faster than IDA.**
(The one exception is the hardest sample, statically linked C++: bindec 10.2 s vs IDA 6.4 s.)

**So if all you use is IDA / Ghidra, you will most likely come away feeling "bindec is slow and awkward". In many scenarios that impression is right. We do not intend to gloss over it.**

---

### But as soon as scale comes up, that is no longer true

Try a piece of real-world software — `/usr/bin/qemu-system-x86_64`, 15.5 MB (2026-10 caliber):

| Tool | Coverage | Elapsed | Output |
|---|---|---|---|
| **bindec** | **decodes every byte in full** | **did not finish within a 15-minute window** | — |
| **Ghidra 12.1.4** | from main, at most 20 functions | 261 s | 93,651 bytes (20 functions) |
| **IDA Pro 9.1** | — | — | **produced nothing** (see below) |

What this set of numbers really shows is:

> **At this scale none of the three produced a usable result** — Ghidra got 20 functions but is a very long way from "understanding the whole binary",
> IDA never got off the ground, and bindec did not finish within the 15-minute window.
>
> So the real conclusion is not "who is faster", it is: **at small scale bindec is not slow (often faster),
> but its cost rises superlinearly with binary size, because it promises full coverage.**

### Why does the UI feel fast? Because that is a different thing

Opening a 15 MB binary in IDA / Ghidra day to day feels like "I can start reading code in a few seconds" —
but that is not the same thing as the 15-minute window above. Four reasons:

**① Auto-analysis ≠ decompilation (the crucial one, and the most commonly misunderstood)**

IDA's "auto-analysis" only does: identify function boundaries, strings, cross-references, stack frames. **It does not produce pseudocode.**
Pseudocode is generated the moment you **press F5**, and only for that one function.

So a 15.5 MB binary with a hundred thousand functions can be "open and usable" in seconds —
**because at that moment auto-analysis is still running in the background, and pseudocode is generated on F5: whichever function you look at is the one that gets generated, never all at once.** Ghidra is the same; of its 261 s, nearly all is the analysis phase.

> **A good deal of the UI's "speed" is really "hasn't started working yet".**

**② Triggered on demand, not by what's on screen**

"It only decompiles the functions on screen" is inaccurate. The real mechanism is **on demand** —
the trigger is "the function you pressed F5 on", not the ones your eyes happen to be on.
One function can span several screens, and scrolling past it does **not** trigger anything; of the 20 functions on screen you may not click **any** of them.

**③ Time to first answer ≠ time to completion**

| | Wait for the first line of code | Total elapsed |
|---|---|---|
| **Batch** | the whole pipeline | 762 s (`/usr/bin/bash`, 2026-10 caliber); larger samples fell outside the measurement window |
| **UI** | tens of milliseconds (that one function) | a few minutes, but you are producing output continuously |

**Even with identical total CPU time, the felt difference is orders of magnitude.** One is throughput, the other is latency.

**④ The database is cached**

IDA's `.i64` and Ghidra's project files store the previous analysis, so **the second open is instant**.
Our framework, so that every run starts from the same state, deliberately **deletes** the cache before running.
**Part of the "it's usually fast" feeling is the experience of the second and third open.**

> So a fair comparison should be: same set of binaries, same demand for exhaustive understanding, both starting from zero, both running to completion or to a clear timeout —
> which is exactly the protocol behind every number in this article. And **on the smaller goal of "only answering for what is reachable from main", the other two genuinely are faster**;
> that is the scenario they are better at, and this article does not deny it.

## 8. Cost two: output size and noise

The average output line count over the same 32 tests (**the bindec column was measured on 2026-11-12**; IDA / Ghidra in 2026-10):

| Variant | bindec | IDA | Ghidra |
|---|---|---|---|
| x64 dynamically linked | 104 | **33** | 50 |
| x86 dynamically linked | 100 | **47** | 72 |
| x86 statically linked | 895 | **293** | 427 |
| x64 statically linked | **1136** | 346 | 377 |

Under static linking, bindec's output is 2.1 to 3.3× the other two. The reason is that it has to translate the whole PLT thunk chain —
the static build of `if_else_simple` comes out of bindec at 432 lines, of which the real `main_inner` is 3 lines,
and the rest is glibc prototypes, thunk stubs and 30-odd commented-out internal symbols (38 functions in the whole file).

What this size buys is exactly the goal from chapter 1: **output that needs nothing filled in by a human and goes straight into gcc.**
IDA / Ghidra's line counts are small because they leave the "filling in" to the person reading the code.

## 9. How to reproduce these numbers

The test dataset used by this article is open source: https://github.com/bindeep-lib/DCB

**The test set is self-contained** — 32 source files, no external dependencies, no hidden metadata, with a `build.sh` included.
Clone it and you can generate all 128 test binaries used here:

```bash

# prerequisite: 32-bit support is a hard dependency; without it 64 of the x86_* cases silently become compile failures
sudo apt install gcc g++ gcc-multilib g++-multilib
gcc -m32 -E -x c /dev/null && echo "multilib OK"

cd test_suite
bash build.sh          # expected output: 128 / 128 binaries produced
```

> Every case is a **single file, a single `main`, no external input, no network, no third-party libraries**,
> so the compiled result is reproducible on any machine. The four variants are `x64_dyn` / `x64_static` / `x86_dyn` / `x86_static`
> (32 × 4 = 128).

### Why "runs correctly" has to be checked exit code by exit code

| | Does not compile | Compiles but runs wrong |
|---|---|---|
| When it surfaces | the compiler errors out immediately | **it compiles, it links, the program starts** |
| Who finds it | anyone, at a glance | **only exit-code comparison finds it** |

**A file that does not compile cannot be misused; a file that compiles but computes the wrong thing flows all the way downstream.**
That is why the exit codes were deliberately designed non-zero and far apart — a "return 0 means pass" criterion would score wrongly-running output as passing.

The automated pipeline behind this article (the four stages, the 41 patching rules, the C++ class stub injection, the exit-code comparison) is maintained together with the bindec project;
each round's results land in a timestamped directory (one summary report plus, for every cell, the output and the original error text).

### Run it yourself

Following the four stages above will reproduce the numbers in this article. Taking `enum_basic` as an example, run each of the three tools:

```bash

# 1) record the original program's exit code as ground truth
./bin/enum_basic_x64_dyn ; echo "exit=$?"        # 20

# 2) decompile with each of the three tools (the exact command depends on the tool)
bindec-decompiler bin/enum_basic_x64_dyn -o out_bindec.c

# IDA / Ghidra likewise, each producing a .c

# 3) Pass 1 — compile the raw output directly; this pass rate is the "compiled as-is" column
gcc -c -w -O0 -no-pie out_ida.c -o out_ida.o     # IDA errors out on __fastcall

# 4) source patching (word substitution, adding declarations, injecting the C++ shell) — bindec skips this step

# 5) Pass 2 — recompile, link, execute; this gives the "after patching" column
gcc -c -w -O0 -no-pie out_ida_fixed.c -o out_ida_fixed.o
gcc -no-pie out_ida_fixed.o -o out_ida_fixed && ./out_ida_fixed ; echo "exit=$?"   # should be 20
```

**The pass rate before patching is "compiled as-is"; after, it is "after patching".** Run all 128 cases both ways and you have both columns.

### Notes on compiling decompiled output

```bash
gcc -c -w -O0 -no-pie out.c -o out.o    # -w silences warnings, -O0 preserves behaviour, -no-pie matches the original binary
```

- **Do not use `-fpermissive`** — it swallows errors like `int → pointer` and makes "does not compile" look like it compiles
- **Use `-c` rather than linking directly** — check compiling first, linking second; the two failure modes have different causes
- **`-w` silences warnings, not errors** — `unknown type name 'Color'` is still an error
- **Both passes must use identical compile flags** — otherwise the difference between the two columns is contaminated by flag changes

## Last

This set of numbers is easiest to misread as "bindec decompiles more accurately than IDA". It does not.

The real fact is this: **within the subset all three can compile, all three are equally accurate.** The difference is that bindec has treated
"the output must compile on its own" as a hard requirement from day one, which forces it to do things IDA and Ghidra never need to do —
identify every libc function inlined into a static binary, recover struct layouts that the optimiser erased, and guess what sits behind every jump thunk with no symbol table to consult.

That work is slow, and a lot of it is not done yet. All 128 small programs at the 20 KB scale passing (128 / 128) does not mean "usable on any binary" —
the test set needs to grow toward larger, more realistic binaries next. That is the next hard requirement.

**The position of this article is best closed with the sentence from chapter 1:**

> **"For a human to read, interactive, cross-architecture, partial coverage" → IDA / Ghidra.**
> **"Has to compile, has to run, has to feed automated tooling" → only bindec.**
>
> One binary, two different readers, two different correct answers.
