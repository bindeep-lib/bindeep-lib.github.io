# 编译器版本对反编译的影响：通过10个真实案例说明

同一份 C 源码，用 gcc 9.4.0（Ubuntu 20.04 自带）和 gcc 15.2.0（Ubuntu 26.04 自带）各编译一次，得到两个运行行为完全一致的二进制。把它们喂给反编译器，麻烦就来了：三个反编译器里，有的产物能直接通过编译，有的连编译这一关都过不去；而「编译器版本换了」这件事，在有些产物里几乎不留痕迹，在另一些产物里处处留痕。

这篇文章把「编译器版本对反编译的影响」拆成 10 个真实案例，再用 128 个测试单元（32 个程序 × 4 个变体）的三方同场实测算总账，回答三个问题：哪些差异真的来自编译器版本，哪些只是反编译器自己的资源问题；哪些差异会写进产物文本，哪些只影响语义、文本上看不见；这些差异对「产物能不能重新编译并跑对」影响有多大。

为什么在意「重新编译」：反编译产物不是终点。漏洞分析、补丁验证这类流水线要把产物重新编译回去再运行，编不过就没有下一步。所以这是一个工程问题。

主角是三个反编译器：IDA Pro 9.1、Ghidra 12.1.4 这两款主流工具，以及 bindec 1.0.2。

bindec 1.0.2 是 binforge 平台（https://bindeep.cn/ ）的二进制反编译模块。binforge 面向安全研究员、逆向工程师和协议分析者，主线有两条：精准反编译与漏洞挖掘，bindec 属于前者 —— 把二进制重铸成类型完整、函数名齐全、能重新编译的 C 源码，并同步输出 LLVM IR。它没有交互界面，是给流水线批量调用的，产物因此定位成「给编译器看的编译单元」：能直接进 gcc，重新链接后运行结果与原二进制一致。

本文的判据（反编译 → 重新编译 → 链接 → 运行 → 比对退出码）就是照这个定位定的。三家产物形态不同，同一把尺子量下去对谁更划算，§一 讲产物形态，§三 算总账。

## 📌 一句话答案：10 条案例里 5 条显形

编译器从 gcc 9.4.0 换到 gcc 15.2.0（语言标准从 C17 到 C23），354 个用户函数里 189 个（53.4%）的指令序列发生变化。这 189 处变化在「给人读」的伪 C 产物（IDA / Ghidra 风格）里大多被吸收；真正与版本相关且在产物文本里留痕的，是 10 条案例中的 5 条。换一个判据（产物重新编译并运行比对），差距立刻拉开：128 个测试 cell 三方同场，双通过率 bindec 100%（128 / 128）、IDA 40.6%（52 / 128）、Ghidra 34.4%（44 / 128）；改用 gcc 15.2.0 重新编译产物后，64 位端到端 bindec 64 / 64 不动，IDA 与 Ghidra 各掉 6 个 cell。

10 条案例一览：

| # | 案例 | gcc 15.2 相对 9.4 变了什么 | 在伪 C 里可见吗 | 三家表现 |
|---|---|---|---|---|
| 1 | 栈保护 canary | xor 换成 sub | 条件显形 | IDA 吸收；Ghidra 条件显形；bindec 显形（^ 变 -） |
| 2 | 调用点多一跳 | 实参装载多一跳、顺序反转 | 被吸收 | bindec 必须寄存器级还原，否则编不过 |
| 3 | 符号扩展 | cltd/cdq 替代 sar 惯用法 | 文本不可见、语义可能错 | 必须跑结果比对才能发现 |
| 4 | 函数收尾与帧布局 | rbx 从 push 改为栈槽 | 间接可见（偏移载体） | 三家产物都带偏移痕迹 |
| 5 | 跳转表 | -O0 下默认关闭 | 条件显形 | 本语料无实例，不外推 |
| 6 | DWARF 4→5 | 库类型图消失、析构描述变化 | 显形 | 仅 IDA / Ghidra 受影响，bindec 不依赖 DWARF |
| 7 | vtable 与 EH | C++ 异常清理分支新增 | 显形 | 三家产物都多出分支痕迹 |
| 8 | 库函数识别 | 两版 gcc 之间无差异 | 跨工具差异 | IDA 内置 intrinsic；Ghidra 离线全盲 |
| 9 | __gmon_start__ | 输入侧无差异 | 不显形 | 弱符号不进伪 C |
| 10 | 语言标准 C17→C23 | 缺声明从警告变硬错误 | 显形 | IDA / Ghidra 各掉 6 个 cell |

## 🔬 先说清楚：DCB 语料、gcc 两版与判据

语料：公开测试集 DCB（github.com/bindeep-lib/DCB），32 个源文件 × 4 个变体（x64 / x86 × 动态 / 静态链接），共 128 个测试单元，下文统一叫 cell。32 位故意占一半，编译统一 -O0。

编译器两条轴：gcc 9.4.0（Ubuntu 20.04 默认，C17）与 gcc 15.2.0（Ubuntu 26.04 默认，C23，并显式加 -fzero-init-padding-bits=all）。

判据只有一条，全程不变：反编译 → 重新编译 → 链接 → 运行 → 比对退出码与原二进制是否一致。「编译通过」只看能不能编过；「双通过」要求编译与运行都过。

三件自设的事，先交代清楚，它们影响怎么读后面的数字：

| 自设项 | 谁定的 | 它决定了什么 | 去掉它还剩什么 |
|---|---|---|---|
| 判据口径（编译 + 运行 + 退出码比对） | 我 | 把「产物像不像 C」换成「产物能不能过编译器、跑得对不对」 | 只剩文本对比，案例 3 这类语义差异完全看不见 |
| bindec 项目自维护的回归测试集（135 个用例，32 位只有 6 个，64 位 540 / 540 全绿） | 项目组 | 它是「已知问题清单」：32 位覆盖太薄，很多 32 位缺陷此前不在视野里 | 本文的 32 位发现仍然成立，只是少了「为什么以前没发现」的解释 |
| 对手产物放宽后处理（IDA 27 条正则 + C++ class stub，Ghidra 18 条，bindec 0 条） | 我 | 让 IDA / Ghidra 的产物尽量过编译 | 数字对 bindec 偏保守（详见 §三） |

## 一、伪 C 与编译单元：产物形态决定敏感度

先看一段 IDA 反编译的真实产物（变参函数场景）：

```c
int main(int argc, char *argv[], char *envp[])   // 三个形参是猜出来的
{
  __readfsqword(0x28u);                          // 没有声明
  ...
  // va_list 只是栈槽注释，没有类型来源
```

把这段产物原样交给 gcc，报 9 处硬错误：my_printf、va_start、va_arg、__readfsqword、_stack_chk_fail 全部 implicit declaration；va_arg(args, uint64_t) 因为缺 stdarg.h，宏根本不展开，直接是语法错误。伪 C 的立场是「读者会补全」：类型、声明、宏，留给看代码的人。

bindec 的产物立场不同：它输出一个能独立通过编译的编译单元。缺声明在 C23 下是硬错误；缺宏在任何语言标准下都是硬错误；指针与整数混用是硬错误；声明类型与实际用法不匹配也是硬错误。编译器不体谅任何一方，所以声明、宏、类型必须逐一还原。

立场差异决定了两条主线，后面所有案例都挂在这两条线上：

1. **产物形态决定敏感度。** 伪 C 的观测面是「像不像一段 C」：只要语义等价，指令层面的形态差异大多被吸收，产物文本几乎不动。编译单元的观测面是「机器码长什么样」：每个运算子、每个中间寄存器都要还原成合法 C，形态差异直接落进文本。
2. **版本差异的「可见性」因此分层。** 同一个输入侧差异，在伪 C 里可能完全隐形，在编译单元里必须显式处理，否则产物编不过。

两种形态放在一张表里：

| | 伪 C（IDA / Ghidra） | 编译单元（bindec） |
|---|---|---|
| 给谁看 | 人 | 编译器 |
| 缺声明 / 缺宏 | 假设读者会补全 | 硬错误，产物编不过 |
| 指令形态差异（多一跳、xor 变 sub） | 大多被吸收，文本几乎不动 | 必须显式还原，直接落文本 |
| 对版本差异的敏感度 | 低，代价是编译这一关本来就过不去 | 高，换来的是能重新编译、能运行 |

## 二、10 个真实案例

每个案例先核对输入侧（两个 gcc 编出的二进制到底差没差、差在哪），再看三个反编译器的产物。「可见性」分三档：显形（差异直接落进产物文本）、条件显形（特定条件下才落文本）、被吸收（文本上看不到）。

### 案例 1 · 栈保护（canary）：xor 换成 sub

输入侧：栈保护校验代码，gcc 9.4.0 用 `mov -0x8(%rbp),%rcx; xor %fs:0x28,%rcx; je`，gcc 15.2.0 用 `mov -0x8(%rbp),%rdx; sub %fs:0x28,%rdx; je`。union_basic、multi_dim_array、class_basic 三个程序同形态。

- IDA：整段折叠。union_basic 的产物只剩 `return 10;` 加一个 thunk，校验逻辑完全不可见。典型的被吸收。
- Ghidra：union_basic 渲染出一个恒假的自不等式 `if (*(long *)(in_FS_OFFSET + 0x28) != *(long *)(in_FS_OFFSET + 0x28))`。回输入侧查，根因不在 xor / sub：上游本来就有 `mov %fs:0x28,%rax; mov %rax,-0x8(%rbp)` 两条指令，两个版本的 Ghidra 产物逐字节相同（连 `PTR___stack_chk_fail_00404000` 都一样）。但 virtual_func 里 Ghidra 能区分栈槽与 TLS 值，比较符两版翻转：9.4 产物是 `!=` 加 fail 后 return，15.2 产物是 `==` 加 return 后 fail，语义等价。条件显形。
- bindec：canary 全链路可见。TLS 读取用占位符 `__thread long long __bindec_tls_64_p40`；失败分支还原成 `#define function_401040() __stack_chk_fail()`；main 用 `__attribute__((optimize("no-stack-protector"))) int main_inner` 防止栈保护被重新灌入；两次 TLS 读取还原成 v2 / v10 两个变量；xor 还原成 C 的 `^`（15.2 版对应 `v10 = v2 - v8`，与输入侧的 sub 对应）；`if (!v12)` 不折叠，原型与调用齐全。栈保护机制完整保留。

这一案例还区分了「看不见」的两种含义：IDA 是吸收（差异进了它的抽象层）；案例 9 会看到另一种，反编译器没有对应的那根神经。

### 案例 2 · 调用点多一跳：伪 C 抹平，编译单元必须显式还原

输入侧：variadic_printf 的 main 从 14 条指令变 15 条。gcc 15.2.0 把 `lea …,%rdx` 提前，新增 `lea …,%rcx; mov %rcx,%rdi` 这一跳，实参装载顺序整体反转。这类「lea 之后多插一条 mov 拷贝」的形态占 189 个差异函数的 16.9%（宽松口径 39.2%）。

- IDA / Ghidra：吸收成 `my_printf("x=%d, y=%s\n", 42, "hello")`（42 与 0x2a 只是写法差异），多出的一跳消失。
- bindec：必须在寄存器级还原形参与实参的对应关系。识别不出来，产物就编不过，这是硬要求。

### 案例 3 · 符号扩展：文本不可见，语义可能错

输入侧：gcc 15.2.0 用 cltd / cdq 指令做符号扩展，gcc 9.4.0 用 `sar $0x1f,%eax` 惯用法，占 189 个差异函数的 1.6%。

128 个变体的三方产物里检索 cdq、cltd、idiv、sar，全部 0 命中：这个差异不以文本形式出现，只以语义结果出现，例如 `v29 = &v44[v28 / 2];`（func_ptr_dispatch 的 IDA 产物）。它是 10 条里唯一「文本不可见、值语义可能错」的案例：如果把 cltd 误建模成 0 扩展，负数被除数会算错，而产物文本仍然是 `/ 2`。伪 C 抹平了文本，抹不平语义，所以「运行比对」这一步不可省。

### 案例 4 · 函数收尾（epilogue）：帧布局变化的间接载体

输入侧：class_basic 的 main 从 38 条变 37 条。gcc 9.4.0 收尾用 `add $0x18,%rsp; pop %rbx; pop %rbp`，gcc 15.2.0 用 `mov -0x8(%rbp),%rbx; leave`：rbx 从 push / pop 改成栈槽存取，函数帧布局随之改变。

- IDA：`int arr[2][3][4]; // [rsp+10h] [rbp-70h] BYREF`，变化落在注释的偏移上。
- Ghidra：`uint8_t local_b8 [8]; uint64_t local_b0; local_a8; …`，按偏移命名局部变量。
- bindec：帧布局是还原局部变量与实参的基础输入。实现上的判别因子是「这个槽是栈槽还是寄存器」，与写入发生在哪个基本块无关，因此对这类帧布局变化不敏感。

差异本身不直接可读，但它是栈槽偏移的载体，算间接可见。

### 案例 5 · 跳转表：条件显形，本语料无实例

输入侧：gcc 15.2.0 在 -O0 下默认关闭跳转表（`-fjump-tables [disabled]`），密集 switch 会退化成决策树。但 DCB 里唯一的 switch_case 是稀疏 case（值 1..5），gcc 9.4.0 本来就生成决策树，这个用例输入侧两版相同。

- IDA：`return 15;`。
- Ghidra：`return 0xf;`，另报 4 条 `WARNING: Removing unreachable block (ram,0x00401142)`。
- bindec：有两套跳表还原能力：跳转表推断，以及 .rodata 字节数组分发表识别。

本语料没有触发跳转表差异的实例，这一条只登记现象，不外推。

### 案例 6 · DWARF 4→5：库类型图消失，析构描述变化

输入侧：gcc 9.4.0 写 DWARF4，gcc 15.2.0 写 DWARF5（DW_UT_compile）。业务类型两版都在：Point 1 个 struct 3 个 member、enum 1 个、union 1 个含 2 member、Counter 增加 1 个 member；types.c 的自造类型 Own / UsedHdr / used_hdr_t 共 2 个 struct / 1 个 typedef / 4 个 member。变的是库类型图：在只用 printf 的那个源文件里，gcc 9.4.0 的 DWARF 带 FILE / _IO_FILE / _IO_marker / _IO_codecvt / _IO_wide_data 加 32 个 member，gcc 15.2.0 里这些全部消失（struct、typedef、member 计数全为 0）。机制在外部变量 DIE：gcc 9.4.0 会为 stdin / stdout / stderr 写 DW_TAG_variable，把 FILE 类型图拖进来；gcc 15.2.0 不写了。DW_AT_frame_base 两版都是 DW_OP_call_frame_cfa，与版本无关。

- Ghidra：保留 DWARF 原型注释，20 个文件共 54 处，如 `/* DWARF original prototype: void Counter(Counter * this, int v) */`，产物里有 `Point p;` / `Color c;` / `U u;` / `Counter c;`。库类型图消失后，靠 DWARF 拿类型的那条路，风险在 Ghidra 一侧。
- IDA：0 处原型注释。struct_basic 直接常量折叠成 `return 60;`；C++ 用例保留 `Counter c; // [rsp+4h] [rbp-1Ch] BYREF` 加 `Counter::Counter(&c, 10);`。
- bindec：有「DWARF 解析崩溃就跳过、退回符号表」的兜底，触发面窄（可变长数组加少数 DWARF5 编码），触发时 stderr 有告警 `Warning: DWARF loading crashed ..., skipping DWARF info.`，不是静默吞掉。实测 gcc 15.2.0 的 struct_basic 无告警，产物与 9.4 版逐行相同（`uint32_t p = 10;`，变量名 p 来自 DWARF，结构体被摊平成标量）。库类型不依赖 DWARF：`FILE *f = stdin;` 的用例，bindec 自动产出 `#include <stdio.h>`、`uint64_t f = stdin;`、`fputc(120, (FILE *)f);`，类型来自它自带的头文件。

意外发现：析构函数 ~Counter（linkage name `_ZN7CounterD4Ev`）的 DW_TAG_formal_parameter，gcc 9.4.0 写了两个（this 与 int，都带 DW_AT_artificial），gcc 15.2.0 只写一个（this，第二个条目是 Abbrev Number: 0）。Ghidra 的析构签名因此两版不同：`Counter::~Counter(&c,__in_chrg);` 加 `void __thiscall Counter::~Counter(Counter *this,int __in_chrg)`，对比单参数版 `Counter::~Counter(&c);`。Ghidra 在这个用例的 5 行差异全部来源于此；IDA 两版逐字节相同。这里只声称「DWARF 描述不同」，ABI 本身未验证（objdump 没有定位到该符号，无直接证据）。

### 案例 7 · vtable 与 EH：清理分支是语义可见的大头

输入侧：virtual_func 的 main 从 49 条变 62 条。gcc 15.2.0 在 operator new 调用点后插入 `mov $0x0,%eax; test %al,%al; je` 与 operator delete 清理分支，这是 C++ 异常处理的 landing pad：-fno-exceptions 下消失，-fno-check-new 下仍在，可以排除「分配失败检查」这种解释。vtable 取址的临时寄存器从 9.4 的 %rdx 链换成 15.2 的 %rax 链。两个版本之间 53.4%（189 / 354 个用户函数）的指令序列变化，在伪 C 层的主要可见形态就是这类新增分支。

- IDA：`LODWORD(v4) = (*((int64_t ( **)(Circle *))shapes->_vptr_Shape + 2))(shapes);`；另多出 `int64_t operator new(uint64_t a1)` 与 `void operator delete(void *a1, uint64_t a2) { _ZdlPvm(a1, a2); }`。
- Ghidra：`iVar2 = (*(this->super_Shape)._vptr_Shape[2])(this);`；vtable 赋值 `(_func_int_varargs **)&PTR__Square_00403d68`；operator new 走 GOT（`PTR_operator_new_00404018`）；多出 operator_delete 与 2 条 `unreachable` WARNING（ram,0x004011b9）。

两个容易误读的点：

1. 带地址的符号名是 diff 噪声。gcc 9.4.0.2 换到 9.4.0.3，仅点版本变化就让 `PTR__Square` 从 00403d68 挪到 00403d50；而 9.4 与 15.2 两个大版本之间恰好没变（两版都是 00403d50）。地址变不变取决于布局，不跟版本轴走。
2. 槽号（`+ 2` / `[2]`）由类布局（DWARF）决定，两版不变：Ghidra 产物里 `[2]` 每版出现 2 次。

### 案例 8 · 库函数识别：跨工具差异，两版 gcc 之间无差异

输入侧：两个版本的二进制里，库函数本身没有版本差异。肉眼可见的差异出在反编译器的资源侧：

- IDA：签名库 sig/pc/ 目录共 137 个 .sig，没有 gcc 版本专属的 x64 集，唯一带 gcc 名字的文件 gcc32rtf.sig 与 gcc-on-linux 无关。同一段 canary 字节，IDA 产出 `v7 = __readfsqword(0x28u);`，来自 Hex-Rays x86 处理器模块的内置 intrinsic，与 gcc 版本无关，全部语料 42 个文件 188 处。PLT 桩则是自指递归 thunk：`int vprintf(...) { return vprintf(format, arg); }`。
- Ghidra：安装包里 FID 库为 0 个 .fidb（FID 要联网、按处理器加编译器加版本下载，离线等于没有库函数识别）。同一段字节产出 `lVar1 = *(long *)(in_FS_OFFSET + 0x28);`，26 个文件 373 处；另有 8 个 C++ 用例命中 __readfsqword，合计 32 个文件 64 处。PLT 桩走 GOT 间接：`PTR_vprintf_00404020`。
- bindec：走「宽覆盖、宁可慢」路线，编译器专属模式只认单一版本，靠通用签名兜底，扫描期偏慢，换来离线可用，这对自动化流水线是刚需。

结论：这一条肉眼可见的差异（IDA 与 Ghidra 对同一段字节给出不同的名字）属于「资源可得性」，容易被误读成「编译器版本」；两个 gcc 版本之间没有变化。

### 案例 9 · __gmon_start__：输入侧根本没有差异的伪差异

输入侧：两个版本都有 __gmon_start__，属性同为 WEAK UND（130 / 130 与 133 / 133 的产物全部带上），这是 crt 与 glibc 的属性，与编译器版本无关。32 × 4 变体的三方产物里，它出现 0 次：弱符号不进伪 C。

bindec 侧有一个注意点：ELF 里它是函数，但 crt 的 _init 把对应 GOT 项当数据读，既是函数又被当数据，原型无处安放，产物只剩裸名字，C 编译时报 undeclared。判据要落在「它被当作什么使用」上，符号表里标的是什么反而是次要的；bindec 侧这个悬空引用在链接期失败，两版表现一样。

本案例的教训：版本差异必须先在输入侧独立核实（objdump / readelf），不能从工具产物反推。案例 7 的地址噪声、案例 8 的资源差异，都容易从这一步误起。

### 案例 10 · 语言标准 C17→C23：缺声明从警告变硬错误

输入侧：DW_AT_producer 从 `GNU C17 9.4.0` 变成 `GNU C23 15.2.0 … -fzero-init-padding-bits=all`。把 32 个 x64 动态变体的产物分别用两个 gcc 编译：

| 产物来源 | gcc 9.4.0 下编过 | gcc 15.2.0 下编过 | 两版都挂 | 只在 C23 挂 |
|---|---|---|---|---|
| IDA | 16 / 32 | 10 / 32 | 16 个 | 6 个 |
| Ghidra | 11 / 32 | 8 / 32 | 21 个 | 3 个 |
| bindec | 32 / 32 | 32 / 32 | 0 个 | 0 个 |

失败性质不同：IDA / Ghidra 的新增失败全是缺声明（implicit declaration of process / compute / classify）—— C17 下这只是 warning，C23 下变成硬错误，所以 IDA 从 16 / 32 掉到 10 / 32、Ghidra 从 11 / 32 掉到 8 / 32。bindec 两版都是 32 / 32：它不走隐式声明这条路 —— 上一轮 bindec 在这一栏的失败是类型不合法（`initialization of 'uint64_t' from 'char *'`、`passing argument 1 of 'longjmp' from incompatible pointer type`），而不是缺声明；那批类型问题修完之后，两版都干净通过，一个都不掉。

64 位端到端成绩单见 §三：bindec 64 / 64 不动，IDA 与 Ghidra 各掉 6 个，此处不重复。

### 小结：与版本相关且在伪 C 留痕的是 5 条

| 案例 | 显形方式 |
|---|---|
| 1 canary | 条件显形（bindec 反而可见：^ 变 -） |
| 5 跳转表 | 条件显形（本语料无实例） |
| 6 DWARF | 显形（仅对 IDA / Ghidra 成立；bindec 侧实测不触发） |
| 7 vtable / EH | 显形（形态） |
| 10 C23 | 显形 |

其余 5 条：案例 8 肉眼可辨，但属于跨工具差异；案例 2 被伪 C 吸收（bindec 必须显式处理）；案例 3 文本不可见、语义可能错；案例 4 间接可见；案例 9 输入侧无差异。

## 三、三方同场实测：128 个 cell 的总账

**先把对我们最不利的数字摆出来：** 这一节的数字有两条时间线。上一轮 bindec 在这 128 个 cell 上有 21 个失败，全部集中在 32 位，其中 8 个是反编译器自身崩溃（产物根本产不出来）；随后 bindec 侧修掉了 32 位那批形态缺陷，同一批输入、同一套判据重测，128 / 128 全过。下面这张表是复测之后的结果 —— 失败率是版本的函数，不是语料的函数。

| 口径 | bindec | IDA | Ghidra |
|---|---|---|---|
| 编译通过 | 128 / 128（100%） | 57 / 128（44.5%） | 44 / 128（34.4%） |
| 编译 + 运行双通过 | 128 / 128（100%） | 52 / 128（40.6%） | 44 / 128（34.4%） |
| x64 双通过 | 64 / 64 | 26 / 64 | 22 / 64 |
| x86 双通过 | 64 / 64 | 26 / 64 | 22 / 64 |
| C++ 子集双通过 | 32 / 32 | 0 / 32 | 0 / 32 |
| 失败总数 | 0 | 76 | 84 |
| 其中编译不过 | 0 | 71 | 84 |
| 其中编译过但运行不一致 | 0 | 5 | 0 |

C++ 子集单独说：bindec 编译通过 32 / 32，双通过 32 / 32；IDA 与 Ghidra 全部 0 / 32，一个都编不过。64 位和 32 位上 bindec 都是零失败。

三个结构性结论：

1. 三个工具都能处理的 44 个公共 cell 上，运行一致率 100%（44 / 44）。编译能力与语义还原是两件正交的事。
2. 反过来看更硬：IDA 失败的 76 个 cell、Ghidra 失败的 84 个 cell，bindec 全部通过。不存在任何一个「对手过了而 bindec 败」的 cell —— 这一轮一个都没有。
3. 代价：静态二进制下 bindec 的产物体积约为对手的 3 倍（铺了 glibc / libstdc++ 的桩函数）。

公平性口径：IDA 的产物做了 27 条后处理正则加 C++ class stub，编译加 -fpermissive；Ghidra 18 条；bindec 一条没加。上表数字对 bindec 偏保守。

原样直接编译口径（不做任何修补、不加 -w / -fpermissive）：bindec 从 117 / 128（91.4%）到 117 / 128（91.4%），两版一个不差；IDA 从 56 / 128（43.8%）掉到 41 / 128（32.0%）；Ghidra 从 44 / 128（34.4%）掉到 32 / 128（25.0%）。原因还是缺声明（implicit declaration of apply、double_it undeclared）：C23 下它从警告变成错误，IDA 与 Ghidra 各掉 15 / 12 个 cell。bindec 自己 11 个原样编不过的全是 C++ 严格类型转换（narrowing conversion of '252'、invalid conversion from 'uint64_t' …），24 个 C 用例 96 / 96 全过 —— 产物在严格模式下能不能过编译器，与编译器版本无关，取决于反编译器有没有把类型写对。

（这一轮两版 gcc 的 32 位 C++ 标准头都齐备，没有出现「缺 bits/c++config.h 导致三家同时编不过」需要剔除的 cell，所以这一栏没有剔除项。）

链接口径：对照框架重编一律动态链接（g++ -w -no-pie … -lc -lm -lpthread -lstdc++）。静态输入的原二进制是静态链接的，bindec 产物引用了 shared libc 不导出的内部符号（__wcsmbs_gconv_fcts_c），动态口径下会链接失败；按原模式 -static 重链就能过。所以对照数字比项目自己的回归口径略差，这里如实写明。gcc 15.2.0 的静态轴：动态口径 0 / 32，按原模式静态重链 31 / 32，差别全在链接模式。

换 gcc 版本重新编译产物的端到端成绩（64 位 cell）：

| 产物来源 | gcc 9.4.0 重编 | gcc 15.2.0 重编 | 变化 |
|---|---|---|---|
| bindec | 64 / 64（100%） | 64 / 64（100%） | 不动 |
| IDA | 26 / 64（40.6%） | 20 / 64（31.2%） | 掉 6 个 |
| Ghidra | 22 / 64（34.4%） | 16 / 64（25.0%） | 掉 6 个 |

新增失败全部是缺声明（implicit declaration of compute / process / classify）。bindec 两个方向都是满的：它产出的代码在两版 gcc 下都编得过，也都跑得出同样的退出码。

### 上一轮那 21 个失败：形态、明细与两份独立佐证

这一段留作对照。上一轮 bindec 在这 128 个 cell 上确实有 21 个失败，全部集中在 32 位：8 个反编译器自身崩溃（C++ 的 try_catch / inherit_single / virtual_dtor / virtual_func，产物产不出来）；10 个 SIGSEGV（func_ptr_callback、struct_return_large / small、class_basic、template_class）；2 个结果不对（variadic_sum 求和错）；1 个环境异常（variadic_printf 的 32 位静态变体，手工重链后正常，属执行环境问题）。归纳成四类形态：cdecl 结构体按值返回（sret）、变参 va_list、函数指针传结构体、C++ 析构与虚表。

佐证一：bindec 项目回归语料里同名程序的注释早就记录过这些形态（「32 位下结构体返回强制走栈拷贝」「变参的栈参数传递翻译错误」「函数指针作为参数时调用约定翻译错误」「不识别分发表」），但对应用例在回归集里只编 64 位。全绿不等于没问题，只是没碰到。

佐证二：干净 32 位环境重编输入后复测。此前那批输入的 32 位链接参数有问题，于是另建干净环境，重编 21 个失败用例的源文件再走同一流程：19 / 21 的失败形态逐字段一致（含 8 个崩溃）；2 个 variadic_sum 都「算错了」但错值不同（栈布局错位）；新输入 21 / 21 编译成功（gcc 9.4.0.2 换 9.4.0.3）。结论：那不是测量误差，也不是输入异常，是当时那一版 bindec 在 32 位上的真实缺陷。

本轮复测：同一批输入、同一套判据，那 21 个失败全部消失，128 / 128，四类形态对应的修复都落在 32 位路径上。留这一段不是为了展示修复速度，而是为了说另一件事 —— 这种「大部分绿、少数红」的分布最容易骗人：全绿的回归集也可能只是没碰到那 21 个用例。

### 产物 byte-diff：32 个 x64 动态变体逐字节对比

（静态变体不作数：libc 内容本身不同。）逐字节相同：IDA 29 / 32（90.6%）、Ghidra 27 / 32（84.4%）、bindec 0 / 32。把产物里的版本注释归一化之后：IDA 29 / 32、Ghidra 27 / 32、bindec 16 / 32（50.0%）。本轮用两版 gcc 各自的产物重测，bindec 仍是 0 / 32、归一化后仍是 16 / 32，与上一轮逐字节一致。

IDA / Ghidra 不同的 3~5 个全是 C++ 用例（inherit_single / virtual_dtor / virtual_func / class_basic / try_catch），来源是案例 7 的 EH 清理分支。bindec 32 / 32 全变：有的只差注释 gcc (9.4.0) 变 gcc (15.2.0)；16 个是代码本身变了（^ 变 -、显式 cast、EH 清理路径）。

机制收尾：伪 C 的产物跟着语义走，编译器版本换了它几乎不动，代价是差异全被吸收、编译这一关本来就过不去；编译单元的产物跟着机器码走，天生对版本差异敏感，换来的是能重新编译、能运行、能把案例 3 那类语义差异暴露出来。

## 四、怎么复现：从 DCB 语料到三方产物重编

### 4.1 两条 gcc 轴

准备 gcc 9.4.0 与 gcc 15.2.0 两套工具链，各自装在独立前缀；测试时把对应版本的 bin 目录放到 PATH 最前，另一套留在 /usr/bin/gcc 作对照。

### 4.2 测试集

```bash
git clone https://github.com/bindeep-lib/DCB
cd DCB && bash build.sh
```

四个变体的编译参数：动态 `gcc -O0 -no-pie -g`；静态 `gcc -O0 -no-pie -g -static -D_GNU_SOURCE=1`；32 位加 -m32（.cpp 走 g++）。注意 -m32 需要 gcc-multilib，缺了它 128 个变体会悄悄全变 64 位。

### 4.3 三个反编译器

```bash
# bindec
bindec-decompiler bin/enum_basic_x64_dyn -o out/enum_basic_x64_dyn.c
```

Ghidra 用 PyGhidra（pip install pyghidra，用 DecompInterface 出伪 C）。IDA 用 idalib（pip install . 之后运行 py-activate-idalib.py，然后 `import idapro, ida_auto, ida_hexrays`）。两个注意点：idalib 绑定 CPython 3.11，且 idapro 必须第一个 import；三个工具必须串行跑（IDA 后端的临时脚本写固定路径，并行会互踩）。

### 4.4 重编译与判据

```bash
gcc -c -w -O0 -no-pie out/foo.c -o foo.o
gcc foo.o -o foo -lc -lm -lpthread
./foo; echo $?
```

退出码与原二进制比对。C++ 产物统一 `g++ -c -w -O0 -no-pie -fpermissive -std=gnu++11` 并加 -lstdc++，另配一个只声明 __stack_chk_fail 与 __readfsqword 的辅助头用 -include 注入，三家一视同仁。静态输入按原模式 -static 重链（__wcsmbs_gconv_fcts_c 这类 hidden 符号动态库不导出）。公平性口径再报一次：IDA / Ghidra 的产物做过放宽修补（官方 __fastcall 宏、C++ class stub 的源码级修补），bindec 一行没补。

### 4.5 输入侧核对

objdump -d 看指令序列；readelf -p .comment 看编译器版本；readelf --debug-dump=info 看 DWARF。Ghidra 12 要 JDK 21（JDK 17 报 unsupported）；FID 库离线为 0 个 .fidb，对应 in_FS_OFFSET 风格的产物渲染。

尾注：bindec 处于 1.0.2 版本；本文所有数字来自同一台测试机的固定环境与固定轮次，按第四节可复现；bindec 是 binforge 平台（https://bindeep.cn/ ）的二进制反编译模块。

## 最后

适用范围先划清：结论只覆盖实测过的组合，DCB 语料的 32 个程序、gcc 9.4.0 与 15.2.0 两版、-O0、x64 与 x86、动态与静态链接。别的编译器、别的优化档位、别的语料，不外推。

给读者的判断标准，两步按顺序来：第一步在输入侧独立核实（objdump / readelf 对照两个版本的二进制），确认差异真的来自编译器版本；第二步再选口径。想知道「差异在产物里留没留痕」，看文本 diff；想知道「产物还能不能用」，只认编译加运行双通过。两个口径会给出相反的观感（byte-diff 一节 bindec 0 / 32 全变，双通过率反而是三家最高），这不是矛盾，是观测面不同。

下一步：bindec 侧 32 位那四类形态已经修完并复测通过，剩下能看到的短板是「原样直接编译」口径下 11 个 C++ 严格类型转换；IDA / Ghidra 用户要过 C23 这一关，给产物补声明是最直接的一步。选哪个反编译器，取决于产物要做什么：给人读，IDA / Ghidra 的伪 C 更友好；要给编译器吃，产物必须先过编译这一关。

想自己动手试：binforge 平台在 https://bindeep.cn/ ，上传二进制即可拿到可重新编译的 C 源码与同步输出的 LLVM IR。
