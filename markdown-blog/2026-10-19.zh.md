# 反编译出来的代码，为什么 IDA 和 Ghidra 的都编不过？

> 128 个测试程序、三方同场实测
> **bindec 1.0.1** / IDA Pro 9.1 / Ghidra 12.1.4 · 同一批二进制、同一套编译命令、同一次运行
> **bindec 1.0.1 为初始版本，反编译执行速度是后续的优化方向之一**

**关于对己不利的数字，本文和 IDA/Ghidra 的失败放在一起写，不分开列、不放附录。**

---

## 📌 一句话答案

**因为三者被要求做的是两件不同的事。**

IDA 和 Ghidra 产出的是**给人看的伪 C** —— 隐含约定是"读代码的人会自己补全缺失的部分"。
bindec 产出的是**给编译器看的编译单元** —— 隐含约定是"编译器什么都不会替你猜"。

**测试的流程只有两步，两步都跑完才是最终成绩：**

**① 把反编译产物原样丢给 gcc** —— 编译、链接、运行。
IDA 的 128 个产物一个都编不过，Ghidra 编过 22 个。

**② 编不过的，做源码修补后再跑一遍** —— 我们替 IDA 写了 23 条正则、
替 Ghidra 写了 18 条，还给两边都生成了 C++ class 壳。

| | ① 原样编译 | ② 修补后再编译 |
|---|---|---|
| IDA Pro 9.1 | **0 / 128** | **57 / 128** |
| Ghidra 12.1.4 | **22 / 128** | **44 / 128** |
| **bindec** | **113 / 128** | **不需要修补** |

---

## 🔬 先说清楚：实验怎么做的

每一个「测试二进制 × 工具」都走这四步，**全文每个数字都来自其中某一步**：

| 步骤 | 做什么 | 测什么 |
|---|---|---|
| **步骤 1** | 反编译 | 得到**原始产物**（反编译器直接吐出来的 C） |
| **步骤 2** | `gcc -c` 原始产物 | 测**原生产物质量** |
| **步骤 3** | 对原始产物做源码修补 | 补声明、换写法、注入 C++ class 壳；**bindec 跳过这一步** |
| **步骤 4** | `gcc -c` → `ld` → 执行 | 测拿去实际能不能用 |

> 这里的 **「源码修补」**，指的是为了通过编译，将伪代码写法换成标准 C 写法，
> 以及补上缺失的声明、注入 C++ class 壳等。

**bindec 走 1 → 4；IDA / Ghidra 走完整 1 → 2 → 3 → 4。**

| 数字 | 来自 |
|---|---|
| 开篇主表 88.3% / 44.5% / 34.4% | 步骤 4 |
| 原样产物的 0% / 17.2% | 步骤 2 |
| 写法问题 / 语义问题分层 | 步骤 2 |
| 失败原因分布、缺声明/缺类型占比 | 步骤 4 |

> ⚠️ **开篇那张主表来自步骤 4，不是"原封不动丢给 gcc"。**
> 我们替 IDA / Ghidra 做了 23 条 / 18 条正则，还生成了 C++ class 壳 ——
> **只有 bindec 的产物是直接进 gcc 的。** 第四章会把这部分影响单独量化。

**关于数据来源的交代：**

- 被测版本：**bindec 1.0.1（初始版本）** / IDA Pro 9.1 / Ghidra 12.1.4。
  **换版本结论可能变** —— 本文所有百分比都对这三个具体版本负责。
  本文测的是 bindec 的**初始版本 1.0.1**，后续版本更新后它的成绩会提升，
  **尤其是反编译执行速度**（见第八章的规模曲线）；但 IDA 和 Ghidra 同样会更新。
- 128 个测试程序 × 3 个工具 = 384 次反编译，**同一次运行**，不是跨时点拼接的。
- 编译命令三方完全对称：`gcc/g++ -c -w -O0 -no-pie [-m32]`，C++ 额外加 `-fpermissive -std=gnu++11`。
- 测试数据集已开源：https://github.com/bindeep-lib/DCB

## 一、先回答一个问题：谁真的需要「能编译」？

动手讲数据之前，有个绕不开的问题：

> **反编译出来的代码，不就是给人看的吗？为什么非得它能编译？**

不回答这个问题，后面所有讨论都是悬空的。

### 1.1 「能读懂」和「能编译」，是两回事

**「能读懂」是给人用的。** 你看到一行注释写着"未知调用约定，但参数存储已确定"，你知道作者自己也没把握，
然后脑补一下就过去了，并不用太在意。

**「能编译」是给机器用的。** 编译器不会脑补。它看到一个叫 `Color` 的变量，就必须找到 `Color` 的定义；
看到一个 `operator_new(...)` 调用，就必须能找到这个函数。**找不到就报错，一个字都不多给。**

打个比方：

| | 伪 C（pseudocode，给人读） | 编译单元（给机器读） |
|---|---|---|
| 隐含约定 | 读者是人，**他知道怎么补全** | 读者是编译器，**它什么都不替你猜** |
| 类比 | 一本给行家看的菜谱 | 一份给机器执行的施工图 |
| 写「适量食盐」 | 读者自己掌握 | **直接编译失败** |
| 写「食盐 3 克、铸铁锅、180℃」 | 也能读懂 | ✓ 照着做就对 |

一句话总结：

> **IDA 和 Ghidra 给你的是前者，bindec 给你的是后者。这不是能力高低，是产品定位不同。**

### 1.2 到底谁真的需要「能编译」？

反编译代码的用途大致分三类。**它们对「可编译」的要求，差别很大。**

#### ❌ 不需要：单点分析

**恶意样本分析。** 你只想知道这个可疑程序干了什么。看看行为、跑跑沙箱、读几个关键函数，就够了。

这种场景下，IDA 和 Ghidra 的按需反编译**明显更快** —— 你问哪个函数，它才解哪个函数，不问不动。
这也是绝大多数人日常用反编译器的方式。

#### ⚠️ 部分需要：定向审计

**商业软件审计。** 你只审关心的那几个模块，比如支付、鉴权，不需要整个二进制的完整源码。

被审的那部分，IDA 能编过。用 IDA 完全没问题。

#### ✅ 必须可编译：全量、自动化

下面这几个场景，**「编不过」不是小瑕疵，而是整条链路直接断掉**。

**① 自动化漏洞扫描**

这是最典型的例子，因为它背后是整个行业的一处**能力不对称**：

- **源码级**扫描器已经很成熟了，远超**二进制级**扫描器的能力 —— Clang Static Analyzer、CodeQL、Semgrep、cppcheck，检查器越做越细
- **大模型**读源码的水平，也远高于它直接读二进制的水平

两边一叠加，结论就出来了：**只有先把二进制还原成源码，才谈得上扫。**

```text
二进制
  |
  ↓  反编译 —— 编不过，就全断在这一步
  |
源码  →  SAST 引擎 + 大模型  →  漏洞报告
```

> SAST：Static Application Security Testing，静态应用安全测试。也就是不运行程序、直接扫源码找漏洞的那一类扫描器。

而这些工具**全都只吃源码，不吃伪 C**。编不过的函数，引擎根本无法处理。

更要命的是**反编译的完整性**。

100 个函数里编不过 20 个，那 20 个函数里的漏洞就永远不会出现在报告里 —— 而且扫描器不会提醒你"有 20 个函数我没看到"。

> **一个编不过的函数，对扫描器来说等于不存在 —— 哪怕那里藏着最严重的漏洞。**

**② 老代码迁移 / 遗留系统维护**

原厂倒闭、编译器太老、硬件停产。你想在新系统上重建一个老程序。

这里的门槛比 ① 更高：① 只需要能编译，② 需要编出来的东西**能链接、能跑**。

而"迁移"的定义就是"编出一个新的二进制" —— 编不出来，剩下的工作量就不是维护，是**从头重写**。

**③ AI 训练语料**

最该被问、也最容易被含糊过去的问题是：**「为什么不直接用源码训？」**

**因为很多情况下，源码根本不在选项里。**

闭源软件、工控固件，只有二进制；游戏和商业库只分发二进制；还有些项目源码曾经公开过、如今仓库已删，只剩二进制。

训练语料的瓶颈从来不是"质量最好的那批代码" —— GitHub 上随时都有 —— 而是**你能稳定、合法、大规模拿到的那批**。

而且，当模型本身就要读二进制的时候（漏洞挖掘、逆向分析、二进制修复、闭源问答），拿源码去训就是
**训练分布和推理分布对不上**。训出一个只会读 `.c` 的模型，扔给它 `.so`，什么都不会。

> `.c` 是 C 语言的源码文件，`.so` 是编译之后的动态库文件。训练时只见过一类，推理时却要处理另一类，
> 等于让模型拿错误的经验去推断。

更关键的是，这类任务的标准答案在二进制那边 —— 源码说的是"作者**想**做什么"，二进制说的是"**实际跑**的是什么"。

**④ 二进制改写 / 二进制修复**

先厘清一件事：**打补丁**和**改写 / 修复**是两回事。

打补丁 —— 直接在二进制上改字节 —— **不需要**源码。一个十六进制编辑器就能把 `74`（`je`）改成 `75`（`jne`）。
所以「二进制打补丁」恰恰是**不需要**可编译源码的场景，本节的论点对它不适用。

真正的需求是**改写 / 修复**：原厂不维护了、源码拿不到，但你必须改变这个程序的行为 ——
给一处越界访问加边界检查、把硬编码的密钥换成外部注入、给一个老函数插探针，看看它到底什么时候被调用。

这些改动都是**语义级**的。你不是在翻转一个标志位，你是在改变程序逻辑。

要可靠地完成，路径只有一条：**反编译 → 修改源码 → 重新编译 → 替换二进制**。

> 这里的「重新编译」不是可选项，是**唯一选项**。
> 源码编不过，这条路就断了 —— 要么退回打字节补丁（只能做非常局部的改动），要么放弃修复。

### 1.3 所以，差别不在能力，在目标

> **IDA / Ghidra 要的是「看懂你关心的那几个函数」。**
> **bindec 要的是「给你一个能自己编译的代码库」。**

前者是**按需**的。分析师点哪个函数，它才反编译哪个函数；缺的东西，分析师自己在类型管理器里补上，然后接着问下一个。

后者是**批量**的。没人会坐在 bindec 面前点鼠标，它必须自己把**所有** libc 函数原型、**所有**结构体定义、
**所有** PLT 跳板（静态链接时，libc 的每个函数在产物里都会留下一个替身）全部吐出来。

**这条路的代价非常刺眼，本文第八章会专门交代。**

## 二、一个反常识的数字

我们把 128 个小程序编译成二进制，分别交给三个反编译器还原成 C 代码，再把**反编译器吐出来的这些 C**
交给 gcc 编译一遍（`gcc -c` → 链接 → 执行 → 比对退出码）。

| | 反编译产物**直接**编译 | 经源码修补后编译 | 链接运行后退出码是否正确 |
|---|---|---|---|
| **bindec** | **113 / 128 = 88.3%** | **不需要修补** | **100 / 128 = 78.1%** |
| IDA Pro 9.1 | **0 / 128 = 0.0%** | 57 / 128 = 44.5% | 52 / 128 = 40.6% |
| Ghidra 12.1.4 | **22 / 128 = 17.2%** | 44 / 128 = 34.4% | 44 / 128 = 34.4% |

> **bindec 的第二列是「不需要修补」** —— 它的产物未经任何处理直接进 gcc，第一列和第三列已经是最终结果。
>
> **另外两家的第一列，才是「原样产物」的真实成绩**：IDA 的 128 个产物一个都编不过，Ghidra 只有 22 个编得过。
> 第二列里多出来的数字，是我们替它们做的加工换来的。
>
> 第三列是在各自**能编译的那份产物**上测的 —— bindec 用直接产物，另外两家用修补后的产物。
>
> 这是上面流水线的**步骤 4**。**我们替另外两家做的加工**（IDA 23 条正则 / Ghidra 18 条正则 + C++ stub 生成）
> 具体值多少个 cell，第四章会把这两段测试的差额单独算清楚。

Ghidra 有 106 个测试**连原样产物都编不过**，源码修补后仍有 84 个过不去。编不过意味着什么？
意味着你连"这段程序到底算错了还是算对了"都没机会知道 —— 编译器在第一关就把你拦下了。

在解释这个数字之前，先说一句可能让人扫兴的话：**这不是"bindec 比 IDA 聪明"的故事。** IDA 和 Ghidra 是这个领域最优秀的工具，它们只是被要求做一件完全不同的事。

## 三、两种产物天差地别

反编译器的产物有两种，区别比多数人以为的大得多。

### 第一种：伪 C（pseudocode）—— IDA / Ghidra 的产物

它的隐含约定是：**"读者是个人，而且这个读者知道怎么补全缺失的部分"**。

打个比方，它像一本**给行家看的菜谱**：

> "取适量食盐""中火慢煮 20 分钟"

你完全看得懂它在做什么，但你没法照着做 —— 多少克？多大火？什么锅？

Ghidra 甚至会直接给你留一句注释：

```c
/* WARNING: Unknown calling convention -- yet parameter storage is locked */
```

翻译过来就是：**"我不知道这个函数怎么传参数，但我先按我猜的方式写上了。"**

### 第二种：编译单元（translation unit）—— bindec 的产物

要求是：**"读者是一台编译器，它什么都不会替你猜"**。

同一本菜谱，但每一步都写死：食盐 3 克、铸铁锅、中火 180℃、煮 20 分钟。缺一样都不行 —— 但只要齐全，谁都能照着做。

所以 IDA 的作者从不担心"这个结构体叫什么名字"，因为分析师会在 IDA 里点开类型管理器自己填。bindec 没有交互界面，它必须自己把所有 libc 函数原型、所有结构体定义、所有 PLT 跳板全部吐出来。

> **88.3% 和 44.5% 的主要来源 —— 不是反编译得更准，是产物定位不同。**
>
> 但这是我们的**假设**，不是结论。下一章把两段测试的账算出来，看它成不成立。

---

## 四、⭐ 做了修补，为什么还是编不过？

上面那些"缺声明""缺类型"，读起来像是"另外两家不行"。但有个公平性问题必须先摆上台面：

> **为了让 IDA 和 Ghidra 的产物可以编译，我们做了哪些修补？**

答案很直接：**补得不少。** 对比框架对 IDA 和 Ghidra 的产物做了这些加工：

| | IDA 路径 | Ghidra 路径 | bindec |
|---|---|---|---|
| 源码修补正则规则数 | **23 条** | **18 条** | **0 条** |
| 生成 C++ class stub | 有（注入到 32 个测试组合） | 有（注入到 32 个测试组合） | 无（自己 emit） |
| 编译时加 `-fpermissive` | 有 | 有 | 有 |

这 41 条规则**没有一条是在"修代码"**，全部只是**对产物做文本替换** —— 把反编译器自造的词换成 gcc 认识的。按用途分四类：

**① 删掉 MSVC 调用约定（IDA 5 条）**

```python
re.sub(r'\b__fastcall\b',    '', content)
re.sub(r'\b__cdecl\b',       '', content)
re.sub(r'\b__stdcall\b',     '', content)
re.sub(r'\b__thiscall\b',    '', content)
re.sub(r'\b__vectorcall\b',  '', content)
```

这五个词是 MSVC 的关键字，gcc 根本不认识。IDA 把它们印在每个函数前面，于是**每一个**产物都过不了编译器的第一关。
> 后面「IDA 0.0%」那个数字，基本就是这 5 条规则造成的：**117 个文件直接解析失败，剩下 11 个栽在别的词上。**

**② 把私有类型名换成标准类型（IDA 16 条 + Ghidra 14 条）**

| 工具 | 替换前 | 替换后 | 条数 |
|---|---|---|---|
| IDA | `_QWORD` / `_DWORD` / `_WORD` / `_BYTE` / `BOOL` | `uint64_t` / `uint32_t` / `uint16_t` / `uint8_t` / `int` | 5 |
| IDA | `unsigned __int64` … `__int8` | `uint64_t` … `int8_t` | 8 |
| IDA | `__noreturn` | 删除 | 1 |
| IDA | `_UNKNOWN` | `void` / `void *` | 2 |
| Ghidra | `undefined1/2/4/8/16`、`undefined` | `uint8_t` / `uint16_t` / `uint32_t` / `uint64_t` / `__uint128_t` / `void` | 6 |
| Ghidra | `sbyte` / `byte` / `word` / `dword` / `qword` | `int8_t` / `uint8_t` / `uint16_t` / `uint32_t` / `uint64_t` | 5 |
| Ghidra | `processEntry` / `__noreturn` | `__attribute__((noreturn))` | 2 |
| Ghidra | `(code *)` | `(void (*)(void))` | 1 |

这一类里，**类型信息其实是全的** —— `_QWORD` 就是 8 字节，`undefined8` 也是 8 字节。缺的只是一个标准 C 的名字，补上就行。

**③ 空白与指针空格规整（IDA 2 条 + Ghidra 2 条）**

```python
re.sub(r'  +', ' ', content)        # 连续空格压成一个
re.sub(r' +\*', ' *', content)      # "int  * x" → "int * x"
```

纯排版。**这类问题 gcc 只是警告，`-w` 一关就没了** —— 但它们会让产物看起来像坏了。

**④ Ghidra 独有的两件事**

| 规则 | 处理 |
|---|---|
| `ram:ff001000` | 换成 `0` —— Ghidra 的伪地址不是真实地址，gcc 没法用 |
| `FUN_00104080` | **查符号表换成真实函数名** —— `nm` 里有的就写回去，没有才保留 `FUN_*` |

**⑤ IDA 在 C++ 测试上额外需要的 4 条规则**（前面那 23 条之外，只对 C++ 生效）

这 4 条不计入上表的 23 条 —— 它们只在 `LANG == "cpp"` 时执行：

| 规则 | 处理 | 为什么需要 |
|---|---|---|
| `RETURN_TYPE Class::method(Type *this) { ... }` | **整段删掉** | IDA 会把成员函数的完整定义也吐出来，只保留 `main` 里的调用就够了 |
| `Counter::~Counter(&c)` | 改写成 `c.~Counter()` | IDA 的析构调用形式 gcc 不认 |
| `void __stack_chk_fail() { ... }` | **整段删掉** | 它与我们注入的 C++ 壳冲突 |
| `{ ; }` 独立空 body | 删掉 | 删完上一条后残留的空壳 |

> 41 条规则里，只有一条用上了二进制本身的信息，其余的全是换词。而按主表的口径，修补之后 Ghidra 仍有 84 个编不过 ——
> **这一类语义缺失的失败，规则再多也救不回来。**

**而 bindec 进行 0 条源码修补 —— 它的产物是直接进 gcc 的。**

### C++ class stub：生成，但只会「保编译」

除了换词，框架还会**生成 C++ 类的壳**。逻辑分三步：

**① 扫描产物里出现的 `ClassName::`**

```python
class_pattern = re.compile(r'\b([A-Z][A-Za-z0-9_]*)\s*::')
referenced_classes = set(class_pattern.findall(content))
```

**② 剔除标准库噪音**（`std`、`string`、`vector`、`map`、`cout`…），剩下的每个类生成一段：

```cpp
class Animal {
public:
    void *opaque_data;        // 不透明数据，挡住真实成员
    void *_vptr;              // 虚表指针
    void *_vptr_Dog;          // ← 给每个被引用的类都加一个虚表指针
    Animal(...) { }           // 构造函数：空实现
    static int speak(...) { return 0; }   // ← 非析构成员一律 static，且永远 return 0
};
```

**③ 插到 `#include <stdint.h>` 之后。**

但这个壳有一个硬伤：**它只能保证「编得过」，保证不了「跑得对」。**

### 两段测试的结果

前面那条流水线不是一次跑完的，它本来就是**测两遍**：

```text
                      ┌───────────── 第 1 遍：原样 ─────────────┐
  IDA/Ghidra: 反编译 ──▶  原始产物 ──▶ gcc ──▶ 0.0% / 17.2%
  bindec:      反编译 ──▶  产物     ──▶ gcc ──▶ 88.3%      （不需要修补）

                      └───────────── 第 2 遍：修补 ─────────────┘
  IDA/Ghidra:          原始产物 ──▶ 源码修补 ──▶ gcc ──▶ 44.5% / 34.4%
```

所以下面这张表读起来很简单：**左列是第 1 遍的成绩，右列是第 2 遍的成绩，中间那段差额是这 41 条规则的功劳。**

同一批二进制、同一套编译命令、同一时间。

| | **第 1 遍**：原样编译 | **第 2 遍**：修补后编译 | 这 41 条规则的贡献 |
|---|---|---|---|
| **IDA Pro 9.1** | **0 / 128 = 0.0%** 🔴 | 57 / 128 = 44.5% | **+44.5 pp** |
| **Ghidra 12.1.4** | **22 / 128 = 17.2%** | 44 / 128 = 34.4% | **+17.2 pp** |
| **bindec** | **113 / 128 = 88.3%** | 不适用（产物本来就是能编译的） | — |

> **bindec 这一行和另外两行不是同一种情况。** 它的产物第 1 遍就编过了，
> 所以没有"修补"这一步 —— 那 41 条规则对它而言是**流水线内置的环节**，不是外挂的补救。

### 步骤 2 失败的 cell，报错落在哪一层？

我们把每个失败 cell 的**第一条** gcc 报错归到两层：

- **写法问题**：工具用了自己的词汇 —— `__fastcall`、`_QWORD`、`undefined8`、`@<n>`、多余空格。跑几条正则就能换成标准 C 写法，**不需要理解程序在干什么**。
- **语义问题**：缺类型定义、缺函数声明、C++ 成员调用方式不对。**必须先搞清楚"这里原本应该是什么"**，也就是必须理解这个二进制。

| | 写法问题 | 语义问题 |
|---|---|---|
| **IDA**（128 个步骤 2 失败） | **96.9%**（117 个是 `__fastcall` 导致的解析失败 + 7 个 `@<n>` 残留） | **0%** |
| **Ghidra**（106 个步骤 2 失败） | 32.1%（Ghidra 专有类型名 `undefined1/2/4/8`） | **56.6%**（32 个缺声明 + 24 个缺类型 + 4 个签名冲突） |

### 决定性证据：生成的 C++ stub 只救回了 2 个

框架里最"聪明"的一环，是给产物生成 C++ 类的壳：

```c
class Counter { public: void *opaque; void *_vptr;
                static int add(int) { return 0; }   // ← 所有成员函数都返回 0
              };
```

我们直接扫产物核对了它的实际效果：

| | 编译通过 | 其中含注入的桩 | 编译失败 | 其中也含桩 |
|---|---|---|---|---|
| **IDA** | 57 | **2** | 71 | 30 |
| **Ghidra** | 44 | **0** | 84 | 32 |

**注入到 64 个产物里（cpp-oop 共 8 个测试 × 4 个变体 = 32 个测试组合，再 × 2 个工具），只救回了 IDA 2 个、Ghidra 0 个。**

而且这 2 个"救回"其实是个陷阱 —— 桩里所有成员函数都 `return 0`，所以它们虽然编译过了，运行时结果必然是错的。
**这 2 个"救回"虽然算编译通过，运行时结果必然是错的** —— 退出码从 13 / 60 变成了 0。

## 五、拆开看：五个真实例子

第四章给了"两层"的结论，但读者还会有一个更朴素的疑问：**具体是哪些东西编不过？**

下面五个例子全部来自本次实测的真实产物，一个字没改（路径已省略）。它们覆盖了失败的主要形态。

> **写法问题** —— C 语法层面的毛病，机器可以批量识别、批量替换。
> **语义问题** —— 涉及"这个类型、这个函数究竟是什么"，信息不在产物里，只能回到二进制里重新读出来。

### 例 1 · IDA：一个词就把整份文件毙掉 —— `__fastcall`

这是最容易理解、也最能说明"写法问题"含义的例子。先看原始源码：

```c
// enum_basic.c
enum Color { RED = 1, GREEN = 2, BLUE = 3 };

int main(void) {
    enum Color c = GREEN;
    int sum = 0;
    switch (c) {
        case RED:   sum = 10; break;
        case GREEN: sum = 20; break;
        case BLUE:  sum = 30; break;
    }
    return sum;  // 期望退出码 20
}
```

**IDA 的步骤 1 产物（未做任何源码修补）全文就 12 行：**

```c
// Auto-generated by IDA Pro 9.1 idalib
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>

// Function: main
int __fastcall main(int argc, const char **argv, const char **envp)
{
  return 20;
}
```

gcc 的反应：

```text
enum_basic_x64_dyn_raw.c:8:16: error: expected '=', ',', ';', 'asm' or '__attribute__' before 'main'
    8 | int __fastcall main(int argc, const char **argv, const char **envp)
      |                ^~~~
```

请注意这件事的分量：**`return 20` 是完全正确的** —— 枚举、switch、三个分支，IDA 一个不落地常量折叠成了 20。
它"输"的原因只是函数名前面多了 `__fastcall ` 这一个词，而这个词是 **MSVC 的调用约定宏，只存在于 IDA 自己的类型库里**，gcc 根本不认识。

对比同一份文件经过我们框架里的一条正则之后：

```c
// Function: main
int main(int argc, const char **argv, const char **envp)
{
 return 20;
}
```

**一个词，0% → 编译通过。** 这就是 IDA 那 96.9% 的"写法问题"失败长什么样：
不是反编译错了，是**IDA生成了编译器不认识的语句**。

### 例 2 · Ghidra：用了类型名，却不给你定义 —— `Color` / `Point`

还是 `enum_basic.c`（源码见例 1），Ghidra 的产物：

```c
/* === main */

/* WARNING: Unknown calling convention -- yet parameter storage is locked */

int main(void)

{
 int sum;
 Color c;

 return 0x14;      // 0x14 = 20，同样是对的
}
```

```text
enum_basic_x64_dyn_ghidra.c:12:2: error: unknown type name 'Color'
   12 |  Color c;
      |  ^~~~~
```

这次更有意思：**Ghidra 认出了 `c` 的类型叫 `Color`**，所以它理直气壮地写了 `Color c;`。
但它**只用了名字，没输出 `enum Color { ... }` 这份定义** —— 因为在 Ghidra 的世界里这无所谓，
分析师可以在类型管理器里自己补。

同样的形态在整个测试集里反复出现：

```text
error: unknown type name 'Point'; did you mean 'int'?     ← struct_basic.c：用户结构体没还原
error: unknown type name 'U'                              ← union_basic.c：用户 union 没还原
error: unknown type name 'binop'                          ← 函数指针 typedef 没还原
```

**注意 `did you mean 'int'?` 这句提示** —— gcc 是把 `Point` 当成一个未声明的标识符去猜的了。
产物里那个 `Point p;` 变量从头到尾没人知道它有几个字节、怎么布局。

**这一类和例 1 有本质区别**：正则改不了它。`Color` 该 RED=1/GREEN=2 还是别的值，
这个信息只存在于原始程序的类型信息里 —— **不读懂那个二进制，就没法凭空造出来**。

### 例 3 · IDA + Ghidra：符号明明在二进制里，却没生成声明

`func_ptr_callback.c` 调用了三个自己写的函数：

```c
int double_it(int x) { return x * 2; }
int triple_it(int x) { return x * 3; }
int add_one(int x)   { return x + 1; }

int apply(int x, int (*op)(int)) { return op(x); }

int main(void) {
    int s = 0;
    s += apply(10, double_it);   // 20
    s += apply(10, triple_it);   // 30
    s += apply(20, add_one);     // 21
    return s;                    // 71
}
```

IDA 的产物：

```c
// Function: main
int main(int argc, const char **argv, const char **envp)
{
 int s; // [rsp+Ch] [rbp-4h]
 int sa; // [rsp+Ch] [rbp-4h]

 s = apply(10, (int (*)(int))double_it);
 sa = apply(10, (int (*)(int))triple_it) + s;
 return apply(20, (int (*)(int))add_one) + sa;
}

// Function: apply
int apply(int x, int (*op)(int))
{
 return op(x);
}
```

```text
error: 'double_it' undeclared (first use in this function); did you mean 'double'?
error: 'triple_it' undeclared
error: 'add_one' undeclared
```

**而这三个函数的符号，在二进制里好好地躺着：**

```console
$ nm func_ptr_callback_x64_dyn
000000000040112e T add_one
0000000000401141 T apply
0000000000401106 T double_it
0000000000401161 T main
0000000000401118 T triple_it
```

名字、地址、符号类型，全都在。**不是"信息丢了"，是"没写出来"** —— IDA 把这三个函数当成了数据（函数指针）
而不是调用目标，所以只为 `main` 和 `apply` 生成了函数体，唯独没给它们生成三行声明。

对照 bindec 的产物，它做了两件事：

```c
// ------------------- Function Prototypes --------------------

static inline __attribute__((always_inline)) uint32_t add_one(int32_t a1);
static inline __attribute__((always_inline)) int32_t apply(int32_t a1, char * a2);
static inline __attribute__((always_inline)) uint32_t double_it(int32_t a1);
static inline __attribute__((always_inline)) uint32_t triple_it(int32_t a1);

// ------------------------ Functions -------------------------

// Address range: 0x401106 - 0x401118
static inline __attribute__((always_inline)) uint32_t double_it(int32_t a1) {
    return 2 * (uint32_t)a1;
}
...
```

**把函数指针当数据引用的地方，就必须补上声明。** bindec 顺带还认出了 `apply` 里那个函数指针分发，
把三个候选目标都解了出来（这一段的 `icall promote` 产物本身很丑，但它能编译、跑对、退出码是 71）。

这一例最能说明两种产物的契约差异：IDA 的假设是"你能在 IDA 里点进去看"，所以它不写声明；
bindec 的假设是"编译器看不见 IDA"，所以必须写。

### 例 4 · Ghidra：把 `this` 当成普通变量 —— 成员函数被写成静态函数

`inherit_single.cpp` 是个最简单的单继承：

```cpp
class Animal {
public:
    virtual ~Animal() {}
    virtual int speak() { return 0; }   // 0 = generic
};

class Dog : public Animal {
public:
    int speak() override { return 1; }  // 1 = woof
};

int main() {
    Animal* a = new Dog();
    int result = a->speak();
    delete a;
    return result;
}
```

Ghidra 的产物里，`main` 长这样（节选）：

```c
int main(void)

{
 int iVar1;
 Dog *this;                    // ← 它声明了一个叫 this 的局部变量
 int result;
 Animal *a;

 this = operator_new(8);
 (this->super_Animal)._vptr_Animal = (_func_int_varargs **)0x0;
 Dog::Dog(this);
 iVar1 = (*(this->super_Animal)._vptr_Animal[2])(this);
 if (this != (Dog *)0x0) {
 (*(this->super_Animal)._vptr_Animal[1])(this);
 }
 return iVar1;
}
```

gcc 一共报了 4 个错，**每一个都不同**：

```text
error: expected unqualified-id before 'this'                    ← this 是 C++ 关键字，不能当变量名
error: invalid use of 'this' in non-member function            ← main 是普通函数，凭什么有 this
error: 'operator_new' was not declared in this scope           ← 它自己前面写的是 operator_new(...)
error: 'super_Animal'                                        ← 继承子对象这个成员，生成的 stub 里没有
```

这里值得单独说的是最后一条。我们框架为了救 Ghidra，会**生成 C++ 类的壳**，大致长这样：

```cpp
class Animal { public: void *opaque_data; void *_vptr;
               void *_vptr_Animal;
               Animal(...) { }
};
class Dog { public: void *opaque_data; void *_vptr;
            void *_vptr_Animal;
            Dog(...) { }
};
```

你一眼就能看出问题：**这个壳只认 `opaque_data` / `_vptr` / `_vptr_<基类>` 三个模式，
而 Ghidra 实际输出的是 `super_Animal` 这种"继承子对象"写法。壳和产物对不上。**

更要命的是，壳里所有成员函数体都是空的 `{ }`，也就是**永远返回未定义值**。
这就是第四章那个"64 次注入只救回 2 个"的由来 —— 就算壳对上了，它也只能保证"编得过"，保证不了"跑得对"。

`inherit_multi.cpp` 上同源的问题长这样：

```text
error: 'class C' has no member named 'super_A'    ← 三层继承，壳里的成员名又对不上了
```

> **这是五个例子里最难的一个。** 它不是"少写了一句声明"，而是 **C++ 对象模型整个不对**：
> 虚表怎么布局、继承子对象放在基类的第几个字节、构造函数做了什么 —— 这些信息在二进制里是有的，
> 但要把它们翻译回 C 能表达的形式，需要的是一个**真正意义上的 C++ 反编译器**，不是加几条正则能做到的。

### 例 5 · IDA：用了只存在于 IDA 内部的宏 —— `LODWORD`

`virtual_func.cpp` 里是虚函数多态。IDA 输出的 `main`：

```c
{
 Circle *v3; // rbx
 Square *v4; // rbx
 Circle *shapes; // [rsp+10h] [rbp-30h]
 Square *shapes_8; // [rsp+18h] [rbp-28h]

 v3 = (Circle *)operator new(0x10u);
 Circle::Circle(v3, 4);
 shapes = v3;
 v4 = (Square *)operator new(0x10u);
 Square::Square(v4, 5);
 shapes_8 = v4;
 LODWORD(v4) = (*((int64_t ( **)(Circle *))shapes->_vptr_Shape + 2))(shapes);
 return (uint32_t)v4 + (*((int64_t ( **)(Square *))shapes_8->_vptr_Shape + 2))(shapes_8) + 2;
}
```

```text
error: 'LODWORD' was not declared in this scope
```

`LODWORD(x)` 是 **IDA 用来表达"取低 32 位"的内部宏**，在 IDA 的类型库里是标准设施。
看起来无害，但它不在任何标准头文件里。

有意思的是**同一个文件里还藏着另一个问题**：

```c
// Function: .__stack_chk_fail
// attributes: thunk
void __stack_chk_fail()
{
 _stack_chk_fail();      // ← 它编了一个自己也不知道对不对的函数
}
```

IDA 给栈保护机制造了个壳，壳的内部调用了 glibc 一个**并未导出**的内部符号 —— 所以
`virtual_func` 这个用例是**编译过了、链接失败**：

```text
/usr/bin/ld: virtual_func_x64_dyn_ida.o: in function `__stack_chk_fail':
undefined reference to `_stack_chk_fail'
```

**这一例是"猜"的典型样本**：IDA 不知道栈保护函数的真实长相，就自己编了一个壳；
而这个壳连它自己都无法验证 —— 因为它调用的目标在 glibc 里根本不导出。

**同一个毛病，在另一个测试 `pointer_arith` 上又出现了一次**：

```text
/usr/bin/ld: pointer_arith_x64_dyn_ida.o: in function `__stack_chk_fail':
undefined reference to `_stack_chk_fail'
```

原因就写在 IDA 自己的产物里：

```c
// Function: .__stack_chk_fail
void __stack_chk_fail()
{
  _stack_chk_fail();      // ← 它编了一个自己也不知道对不对的函数
}
```

### 五个例子归总

| 例子 | 形态 | 属于哪一层 | 修起来难不难 |
|---|---|---|---|
| 1. IDA `__fastcall` | 反编译**是对的**，只是壳不认识 | 写法问题 | **一条正则** |
| 2. Ghidra `Color` / `Point` | 用了类型名，不给定义 | 语义问题 | 难 —— 得知道类型布局 |
| 3. IDA `double_it` | 符号在二进制里，没写声明 | 语义问题 | 中 —— 补声明即可 |
| 4. Ghidra `this` / `super_Animal` | C++ 语义模型整个不对 | 语义问题 | **最难** —— 得是真正的 C++ 反编译器 |
| 5. IDA `LODWORD` / `__stack_chk_fail` | 用了内部宏；且猜错了 | 写法问题 + 语义问题 | 前半一条正则，后半修不了 |

## 六、bindec 赢在哪里

回到第二章那张表，把它拆开看。

### 先把对我们最不利的三个数字摆出来

前六章都在讲 IDA 和 Ghidra 的问题，读者难免会想：**你们是不是挑了对自己有利的指标？**

这一章把最不利的数据摊开算。**对 bindec 最不利的，是这三个数字**：

1. **C++ 那一类最难看。** cpp-oop 里 bindec 只有 **22 / 32 = 68.8% 能编译、15 / 32 = 46.9% 跑对**，是全系列最低的一栏。
2. **32 位明显弱于 64 位。** x86 那一行跑对率掉到 **64.1%**，而 x86-64 是 **92.2%**。
3. **有产物是「编得过、跑不对」的。** 全系列有 **13 个测试编译通过了、运行退出码却不一致**。
   这类问题最容易被藏起来，所以我们放在正文最前面讲。其中最该看的 7 个（全在 C++ 那一栏、全是 32 位），
   在**第八章**单独摊开。

下面按架构和代码难度逐层拆开。

> **下面所有表格都把「编译通过」和「编译后跑对」分开列。** 两个数都要看 ——
> 比如 cpp-oop 里 bindec **22 个能编译，但只有 15 个跑得对**，中间那 7 个正是第七章要交代的部分。
> 只看编译数会高估，只看跑对数会漏掉"产物看起来能用其实会崩"的坑。

### 按架构

|---|---|---|---|---|
| **x86-64** | 编译 | **59/64 = 92.2%** | 31/64 = 48.4% | 22/64 = 34.4% |
| | 跑对 | **59/64 = 92.2%** | 26/64 = 40.6% | 22/64 = 34.4% |
| **x86 32-bit** | 编译 | **54/64 = 84.4%** | 26/64 = 40.6% | 22/64 = 34.4% |
| | 跑对 | **41/64 = 64.1%** | 26/64 = 40.6% | 22/64 = 34.4% |

### 按代码难度（这一栏最能说明问题）

| 类别（测什么） | 指标 | bindec | IDA Pro | Ghidra |
|---|---|---|---|---|
| **c-basic**（if / for / switch / 结构体 / 指针，48 个） | 编译 | **48/48 = 100%** ✅ | 39/48 = 81.3% | 28/48 = 58.3% |
| | 跑对 | **48/48 = 100%** ✅ | 36/48 = 75.0% | 28/48 = 58.3% |
| **c-advanced**（变参、函数指针、goto、setjmp、内联汇编、struct 返回，48 个） | 编译 | **43/48 = 89.6%** | 16/48 = 33.3% | 16/48 = 33.3% |
| | 跑对 | **37/48 = 77.1%** | 16/48 = 33.3% | 16/48 = 33.3% |
| **cpp-oop**（类、继承、虚函数、模板、异常，32 个） | 编译 | **22/32 = 68.8%** | 2/32 = 6.3% | **0/32** |
| | 跑对 | **15/32 = 46.9%** | **0/32** | **0/32** |

c-advanced 那一栏值得再拆一层，因为它藏着一个对结论很重要的细节：

| c-advanced 细分 | 指标 | bindec | IDA Pro | Ghidra |
|---|---|---|---|---|
| x86-64（24 个） | 编译 | **24/24 = 100%** ✅ | 8/24 = 33.3% | 8/24 = 33.3% |
| | 跑对 | **24/24 = 100%** ✅ | 8/24 = 33.3% | 8/24 = 33.3% |
| x86 32-bit（24 个） | 编译 | **19/24 = 79.2%** | 8/24 = 33.3% | 8/24 = 33.3% |
| | 跑对 | **13/24 = 54.2%** | 8/24 = 33.3% | 8/24 = 33.3% |

**bindec 在 64 位上的高级特性（变参、函数指针、goto、setjmp、内联汇编、struct 返回）编译和跑对都是全过的
（各 24/24）；到了 32 位，编译掉 5 个、跑对掉 11 个。** 32 位是我们明确的短板，这也解释了上面"按架构"表里
x86 那一行为什么跑对率掉到 64.1%。

cpp-oop 那一栏差距最大。IDA 只编过 2 个、**跑对一个都没有**，Ghidra 连编译都过不去 —— 注意是**"编译不过"，不是"反编译错"**。
原因很直白：Ghidra 输出 `operator_new` 却没声明它，输出 `runtime_error` 却没定义它，输出 `this->method()` 却在非成员函数里用 `this`。

## 七、那 7 个「编得过、跑不对」

上一章说过一句话，我们在这里兑现它：

> 全系列有 13 个测试编译通过了、运行退出码却不一致。这类问题最容易被藏起来，所以我们放在正文最前面讲。

13 个是全系列的范围，本章只讲其中的 **7 个** —— 它们全部落在 `cpp-oop` 这一类，也就是 C++ 那一栏。

**为什么把它们单独拎出来？** 因为它们的性质和"编不过"完全相反：

| | 编不过 | 编得过、跑不对 |
|---|---|---|
| 什么时候暴露 | 编译器立刻报错 | **编译通过、链接通过、程序起来了** |
| 谁会发现 | 任何人，一眼看见 | **只有比对退出码才会发现** |
| 隐蔽程度 | 零 | 高 —— 程序不崩、不报错，只是结果错了 |

**一个编不过的文件不可能被误用；一个编得过但算错的文件，会一路流到下游。**

### 7.1 这 7 个是什么

它们来自 5 个 C++ 测试文件，**全部是 32 位（x86）**：

| 测试文件 | 变体 | 原程序退出码 | 反编译后 | 差 |
|---|---|---|---|---|
| `class_basic` | `x86_dyn` | 13 | **168** | +155 |
| `class_basic` | `x86_static` | 13 | **24** | +11 |
| `inherit_single` | `x86_dyn` | 1 | **0** | −1 |
| `template_class` | `x86_dyn` | 25 | **76** | +51 |
| `template_class` | `x86_static` | 25 | **140** | +115 |
| `virtual_dtor` | `x86_dyn` | 2 | **−11** | −13 |
| `virtual_func` | `x86_dyn` | 75 | **2** | −73 |

**注意第一行和第七行：**

- `class_basic` 的 `x86_dyn` 从 13 变成 **168** —— 差了一个数量级
- `virtual_func` 从 75 变成 **2**，几乎掉进了另一个测试的正常区间

> **这就是为什么我们的测试程序退出码全部非 0、且有 24 个不同值。**
> 如果当初随手写了几个「返回 0」的用例，这 7 个里有几个会被记成「跑对了」——
> 比如 `inherit_single` 原程序返回 1、反编译后返回 0，**只看「是否崩溃」的话它算通过**。

### 一个必须说清楚的事实

这 7 个**不是 C++ 特有的问题**，而是**32 位特有的**。

| 架构 | cpp-oop 编译通过 | 其中跑对 |
|---|---|---|
| x86-64 | 全部 | 全部 |
| **x86（32 位）** | 22 / 32 | 15 / 32 |

**x86-64 上这 7 个是 0。** 全部问题集中在 32 位这一栏。

这与本文另一条主线吻合：bindec 为了让产物直接进 gcc，必须在 IR 层把 C++ 的对象模型（虚表、继承子对象、
构造函数调用）翻译成 C 能表达的形式。这个翻译在 64 位上做得干净，在 32 位上有几处会算错值。

**我们没有逐个定位这 7 个的确切根因** —— 本章只做一件事：把它们完整摆出来，说明这是 32 位 C++ 路径上的已知短板。

### 7.2 它们为什么危险

**① 不崩溃。**

这 7 个产物全部编译通过、链接通过、程序正常启动并退出。没有任何一个会 segfault 或 abort。

如果测试的判据是"能不能跑起来"，它们的通过率和正确的产物**完全一样**。

**② 下游工具看不见。**

第一章说过，自动化扫描的链路是：

```text
二进制 → 反编译 → 源码 → SAST 引擎 / 大模型 → 漏洞报告
```

这 7 个产物能顺利通过中间每一环。对扫描器来说，"编得过"就等于"可分析"，而**它算错的那部分逻辑，扫描器读到的也是错的**。

**③ 退出码的巧合会骗过人工检查。**

`inherit_single` 原程序返回 1、反编译后返回 0 —— 这一条如果只做「是否等于 0」的判断，会被记成通过。

我们的判据是**逐个比对原程序退出码**，并且特意让 32 个测试的退出码互不相同，就是为了堵这个漏洞。

### 7.3 接下来会怎么处理

坦白讲：**这 7 个是我们已知、还没修完的短板。**

**① 已经在正文里主动交代。**

第六章开篇就写明「13 个测试编译通过了、运行退出码却不一致」，而不是把它藏在附录里。
读者在读到 88.3% 的时候，就有机会先看到这条。

**② 复现体已入库。**

5 个对应的测试程序在开源的测试集里，跑一遍就能复现：

```bash
bash build.sh          # 生成 128 个二进制
# 取 cpp-oop 的 5 个 x86 用例反编译、重编译、运行，比对退出码
```

**③ 会在近期修复。**

这 7 个全部集中在 32 位 C++ 的对象模型翻译上 —— **虚表、继承子对象、构造函数**这三样东西，翻译得还不够干净。

这不是加个脚本能糊过去的：要让产物直接进 gcc，就必须先把这个二进制里「对象是怎么组织的」判断对。修复要回到反编译器本身改。

> **这一章列的 7 个，是我们自己的短板，也是全文里唯一一处「知道错在哪、但还没改完」的地方。**
> **我们会把它补上。**

## 八、⚠️ 代价一：慢，以及慢在哪

前面全是好话，这一章讲代价 —— 而且这个代价相当刺眼。

### 先纠正一个过时说法

我们内部文档里曾经写着"bindec 处理 600KB 静态二进制要 100+ 秒"。**这个数字对当前代码已经过时了。**
我们在同一批测试二进制上实测了三方耗时（每个格子都是同一个二进制上、同一台机器、CPU 空闲时测的）：

| 样本 | 大小 | bindec | IDA | Ghidra |
|---|---|---|---|---|
| `if_else_simple` 动态链接 x64 | 17.3 KB | **0.4 s** | 0.64 s | 1.69 s |
| `variadic_printf` 动态链接 x64 | 19.5 KB | **0.5 s** | 0.39 s | 2.00 s |
| `virtual_func`（C++）动态链接 x64 | 22.0 KB | **0.6 s** | 0.68 s | 1.81 s |
| `if_else_simple` 静态链接 x64 | 853 KB | **2.6 s** | 6.16 s | 33.28 s |
| `variadic_printf` 静态链接 x64 | 855 KB | **3.2 s** | 7.29 s | 35.60 s |
| `setjmp_longjmp` 静态链接 x86 | 694 KB | **2.1 s** | 4.49 s | 35.75 s |
| `virtual_func`（C++）静态链接 x64 | 936 KB | 8.6 s | 6.36 s | 38.09 s |

> 动态链接：程序运行时才去加载 libc；静态链接：编译时就把 libc 整个塞进产物里。
> 所以静态样本体积大出一个量级，耗时也跟着涨。

**在这个规模上，bindec 不比 IDA 和 Ghidra 慢 —— 静态二进制甚至比 Ghidra 快 4 到 12 倍，比 IDA 快 1 到 3 倍。**
（唯一的例外是最难的 C++ 静态样本，bindec 8.6 秒 vs IDA 6.4 秒。）

**所以如果你只用 IDA / Ghidra，你大概率会觉得「bindec 又慢又难用」。这个印象在很多场景下是对的。我们不打算掩饰这一点。**

### 但规模一上来就完全不是这样

拿一个真实世界的软件试试 —— `/usr/bin/qemu-system-x86_64`，15.5 MB：

| 工具 | 处理范围 | 耗时 | 产物 |
|---|---|---|---|
| **bindec** | **全量解码每一个字节** | **15 分钟窗口内没有跑完** | — |
| **Ghidra 12.1.4** | 从 main 出发，最多 20 个函数 | 261 秒 | 93,651 字节（20 个函数） |
| **IDA Pro 9.1** | — | — | **未能产出**（见下） |

这一组数据真正能说明的是：

> **在这个规模上，三家都没有给出可用的产物** —— Ghidra 拿到 20 个函数但离"理解整个二进制"差得极远，
> IDA 根本没跑起来，bindec 在 15 分钟窗口内没有跑完。
>
> 所以真正的结论不是"谁更快"，而是：**小规模上 bindec 不慢（甚至更快），
> 但它的成本随二进制规模线性上升，因为它承诺了全量。**
 
为此在当前版本上补测了从 142 KB 到 1.18 MB 的曲线（**仅 bindec，不参与三方对比**）：

| 真实二进制 | 大小 | bindec 耗时 | 产物 |
|---|---|---|---|
| `/bin/ls` | 142 KB | 23.0 s | 23,430 行 C |
| `/usr/bin/nano` | 320 KB | 100.4 s | 65,503 行 C |
| `/usr/bin/openssl` | 753 KB | 580.8 s | **1,059,662 行** C |
| **`/usr/bin/bash`** | **1.18 MB** | **762.4 s** | **228,988 行** C |

**这就是本文能给的上界：1.18 MB 的真实二进制，762 秒，22.9 万行 C，完整跑完。**
再往上（3 MB、6 MB、16 MB）都在测量窗口内没能跑完 —— 前面那张 15.5 MB 的表已经交代过这件事。

顺便一提，Ghidra 在 16 MB 这个规模上也不快（261 秒），而且它的开销几乎全在自己的**二进制分析阶段**，
而不是反编译阶段 —— 这一点很关键，下一节展开讲。

### 为什么平时用 UI 觉得快？因为那是另一件事

日常用 IDA / Ghidra 打开 15 MB 的二进制，感觉"几秒就能开始看代码"——
但这跟上面那个 15 分钟窗口内没跑完，根本不是同一件事。四个原因：

**① 自动分析 ≠ 反编译（最关键，也最容易被误解）**

IDA 的"自动分析"只做：识别函数边界、字符串、交叉引用、栈帧。**它不产出伪 C。**
伪 C 是你**按下 F5 那一刻**才生成的，而且一次只生成那一个。

所以 15.5 MB、十万个函数的二进制能在几秒内"打开可用"——
**因为那一刻自动分析还在后台跑，而伪 C 是按 F5 触发生成的：你看哪个函数才生成哪个，从来不是一次性全量生成。** Ghidra 同理，261 秒里几乎全是分析阶段。

> **UI 所谓的"快"，有相当一部分其实是"还没开始干活"。**

**② 按需触发，不是按屏幕**

"它只反编译屏幕里的函数"这个说法不准确。真正的机制是**按需** ——
触发点是"你按了 F5 的那个函数"，不是你眼睛看到的那些。
一个函数可以横跨好几屏，滚过去**不**触发；屏幕上 20 个函数你可能**一个都不点**。

**③ 时间到首个答案 ≠ 时间到完成**

| | 看到第一行代码要等 | 总耗时 |
|---|---|---|
| **批处理** | 全流程走完 | 762 秒（`/usr/bin/bash`）；16 MB 落在测量窗口之外 |
| **UI** | 几十毫秒（就那一个函数） | 几分钟，但你在持续产出 |

**即使总 CPU 时间完全一样，体感也差好几个数量级。** 一个是 throughput，一个是 latency。

**④ 数据库被缓存了**

IDA 的 `.i64`、Ghidra 的工程文件存着上次的分析结果，**第二次打开是秒开**。
而我们的框架为了每次从同一状态出发，运行前会**主动删掉**缓存（`run_ida.py:57-62`）。
**"平时很快"的体感里，有一部分其实是第二、三次以后的体验。**

> 所以公平的比较应该是：同一批二进制、同样要求全量理解、同样从零开始、同样跑到完成或明确超时 ——
> 这正是本文所有数字采用的协议。而**"只回答 main 可达的那部分"这个更小的目标上，另外两家确实更快**，
> 那是它们更擅长的场景，本文并不否认。

## 十、这些数字怎么复现

本文使用的测试数据集已开源：https://github.com/bindeep-lib/DCB

**测试集本身是自足的** —— 32 个源文件，无外部依赖、无隐藏元数据，随附一个 `build.sh`。
克隆下来就能生成本文全部 128 个测试二进制：

```bash
# 前置：32 位支持是硬依赖，缺了 64 个 x86_* 会静默变成编译失败
sudo apt install gcc g++ gcc-multilib g++-multilib
gcc -m32 -E -x c /dev/null && echo "multilib OK"

cd test_suite
bash build.sh          # 预期输出：生成 128 / 128 个二进制
```

> 每个用例是**单文件、单 `main`、无外部输入、无网络、不依赖第三方库**，
> 因此在任意机器上编译结果都可复现。四个变体是 `x64_dyn` / `x64_static` / `x86_dyn` / `x86_static`
> （32 × 4 = 128）。

### 自行跑一遍

按前面那四步就能自己跑出本文的两组数字。以 `enum_basic` 为例，把三个工具各跑一遍：

```bash
# 1) 记录原程序退出码，作为 ground truth
./bin/enum_basic_x64_dyn ; echo "exit=$?"        # 20

# 2) 三个工具各自反编译（命令依工具而定）
bindec-decompiler bin/enum_basic_x64_dyn -o out_bindec.c
# IDA / Ghidra 同理，各产出一份 .c

# 3) 第 1 遍 —— 直接编译原生产物，这一步的通过率就是「原样编译」列
gcc -c -w -O0 -no-pie out_ida.c -o out_ida.o     # IDA 会在 __fastcall 上报错

# 4) 源码修补（换词、补声明、注入 C++ 壳）—— bindec 跳过此步

# 5) 第 2 遍 —— 重新编译、链接、执行，得到「修补后」列
gcc -c -w -O0 -no-pie out_ida_fixed.c -o out_ida_fixed.o
gcc -no-pie out_ida_fixed.o -o out_ida_fixed && ./out_ida_fixed ; echo "exit=$?"   # 应为 20
```

**修补之前的通过率 = 「原样编译」，之后的 = 「修补后」。** 把 128 个用例各跑两遍，两列数字就齐了。

### 编译反编译产物时的注意事项

```bash
gcc -c -w -O0 -no-pie out.c -o out.o    # -w 关警告，-O0 保行为，-no-pie 对齐原二进制
```

- **不要用 `-fpermissive`** —— 它会吞掉 `int → pointer` 这类错误，让「编不过」看起来编过了
- **`-c` 而不是直接链接** —— 先看能否编译，再看能否链接，两类失败原因不同
- **`-w` 只关警告，不关错误** —— `unknown type name 'Color'` 这类仍然是 error
- **两遍的编译参数必须一致** —— 否则两列的差异里会混入参数变化

## 最后

这组数据最容易被误读成"bindec 反编译得比 IDA 准"。它不是。

真正的事实是：**在"三方都能编译的那部分"里，三家一样准。** 差别在于，bindec 从第一天起就把
"产物必须能自己编译"当成了硬指标，于是它必须去做那些 IDA 和 Ghidra 从来不需要做的事 ——
识别静态二进制里被内联进来的每一个 libc 函数、还原被优化掉的结构体布局、在没有任何符号表的情况下
猜出每个跳转壳后面是什么。

这些活很慢，很多地方还没做好（32 位 C++ 仍是短板，第八章那 7 个用例就是明证，C++ 模板与异常还有一半过不去）。
但它是自动化流水线能不能落地的前提 —— 因为下游那些漏洞扫描引擎，不会等你手动去 IDA 里补类型。

**本文的立场，用第一章那句话收尾最合适：**

> **「要人读、要交互、要跨架构、只要局部」→ IDA / Ghidra。**
> **「要能编译、要能跑、要喂给自动化工具」→ 只有 bindec。**
>
> 同一个二进制，两个不同的读者，两种不同的正确答案。
